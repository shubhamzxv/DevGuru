<Analogy>

Docker is a **driver** who can drive one bus very well. Kubernetes is the **transport depot manager** for a fleet of buses: decides which bus runs which route, sends a spare when one breaks down, adds buses at rush hour, and replaces old buses with new ones route by route without stopping service.

You need the driver either way. The manager matters when you have a fleet.

</Analogy>

## Simple explanation

They solve different problems, so "Docker **vs** Kubernetes" is a bit of a trick question:

| | Docker (+ Compose) | Kubernetes |
| --- | --- | --- |
| Scope | one host | a cluster of many nodes |
| Job | build images, run containers | **orchestrate**: schedule, heal, scale, update |
| Config | Dockerfile, compose.yaml | YAML manifests (Deployment, Service, ...) |
| Self-healing | restart policy only | replaces failed pods, moves them off dead nodes |
| Scaling | manual | `replicas`, Horizontal Pod Autoscaler |
| Updates | recreate containers | rolling updates and rollbacks |
| Learning curve | small | big |

Kubernetes still runs **container images**: you build them with Docker (or another tool) exactly as before. Since v1.24 Kubernetes talks to containerd directly instead of Docker Engine, but images built by Docker work unchanged (they follow the OCI standard).

**Kubernetes words you should know**

| Term | Meaning |
| --- | --- |
| Cluster / node | the set of machines / one machine |
| **Pod** | smallest unit: one or more containers sharing network and storage |
| **Deployment** | "keep 3 replicas of this pod template running", handles rolling updates |
| **Service** | stable name and IP that load-balances to the pods |
| Ingress | HTTP routing from outside to services |
| ConfigMap / Secret | configuration and secrets for pods |
| Namespace | a folder-like separation inside a cluster |
| HPA | autoscaling pods on CPU or custom metrics |

A minimal Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
spec:
  replicas: 3
  selector:
    matchLabels: { app: shop-api }
  template:
    metadata:
      labels: { app: shop-api }
    spec:
      containers:
        - name: api
          image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/shop-api:1.4.0
          ports:
            - containerPort: 8000
```

`kubectl apply -f deployment.yaml`, `kubectl get pods`, `kubectl logs`, `kubectl rollout undo deployment/shop-api`.

**On AWS** the options are:

- **ECS** (with EC2 or **Fargate**): AWS's own, simpler orchestrator: a great default for small and medium teams
- **EKS**: managed Kubernetes, when you need the Kubernetes ecosystem or portability
- **App Runner**: give it an image, it runs and scales it: simplest of all

When to choose what: one server or local development → Docker Compose. A few services on AWS → ECS Fargate. Many services, multi-cloud, a platform team → Kubernetes (EKS).

## Code example

The same app in both worlds:

```bash
# Docker: one host
docker run -d --name api -p 8000:8000 --restart unless-stopped shop-api:1.4.0

# Kubernetes: a cluster
kubectl apply -f deployment.yaml -f service.yaml
kubectl get pods
kubectl scale deployment shop-api --replicas=5
kubectl set image deployment/shop-api api=shop-api:1.5.0
```

<InterviewQA>

<QA q="What is the difference between Docker and Kubernetes?">

Docker is a tool to build container images and run containers on a single host. Kubernetes is a container orchestration platform that runs containers across a cluster: it schedules pods onto nodes, keeps the desired number of replicas running, restarts or reschedules failed ones, provides service discovery and load balancing, autoscaling, configuration and secrets, and rolling updates and rollbacks. They are complementary: Docker-built images run on Kubernetes.

</QA>

<QA q="What is a pod?">

The smallest deployable unit in Kubernetes: one or more tightly coupled containers that share a network namespace (same IP and ports) and can share volumes, scheduled together on one node. Usually one app container per pod, sometimes with sidecars.

</QA>

<QA q="ECS or EKS?">

ECS is AWS-native, simpler to run and integrates tightly with IAM, ALB and CloudWatch; with Fargate there are no servers to manage, which suits most small and medium teams. EKS gives standard Kubernetes with its large ecosystem (Helm, operators, service meshes) and portability across clouds, at the cost of more complexity.

</QA>

<QA q="Did Kubernetes drop Docker?">

Kubernetes removed dockershim in version 1.24 and now uses CRI runtimes such as containerd directly. Images built with Docker are OCI images and keep working; only Docker Engine as the node runtime was dropped.

</QA>

<CheatSheet>

| Need | Choose |
| --- | --- |
| Build images | Docker |
| Local dev, one server | Docker Compose |
| AWS, few services | ECS Fargate / App Runner |
| Large platform, ecosystem, multi-cloud | Kubernetes (EKS) |

| Kubernetes | Meaning |
| --- | --- |
| Pod | container(s) unit |
| Deployment | replicas + rolling updates |
| Service | stable name, load balancing |
| Ingress | outside HTTP routing |
| ConfigMap / Secret | config / secrets |
| `kubectl apply / get / logs / rollout undo` | daily commands |

</CheatSheet>
