<Analogy>

Think of a library book with a slip that counts how many people are holding a copy on loan. Each new borrower adds one. Each return removes one. When the count reaches zero, the book goes back on the shelf for others.

Sometimes two members keep lending the same book to each other and never return it. So once in a while a librarian walks around and collects such forgotten books.

The loan slip is **reference counting**. The librarian's round is the **garbage collector**.

</Analogy>

## Simple explanation

In languages like C, the programmer must ask for memory and give it back. In Python, this is **automatic**.

All Python objects live in a private area of memory called the **private heap**. The interpreter's **memory manager** controls it.

Python (the standard CPython) uses two mechanisms to free memory.

**1. Reference counting.** Every object stores a number: how many **references** (names, list slots, attributes) point to it.

- The count goes up when you assign the object to a new name or put it in a container
- The count goes down when a name is deleted, reassigned, or goes out of scope
- When the count reaches **zero**, the object is destroyed **immediately** and its memory is freed

**2. Garbage collection.** Reference counting cannot handle a **reference cycle**: two objects that point to each other. Their counts never reach zero, even when nothing else uses them. A separate **garbage collector** (the `gc` module) runs from time to time, finds such unreachable cycles, and frees them.

The garbage collector is **generational**. New objects are checked often. Objects that survive are moved to older generations and checked less often, because old objects tend to stay.

Small objects are also served from memory pools that Python keeps ready, which makes creating and destroying them fast.

## Code example

```python
import gc
import sys

data = [1, 2, 3]
base = sys.getrefcount(data)             # the count right now

alias = data                             # one more name points to the list
holder = {"key": data}                   # a dict value points to it too
print(sys.getrefcount(data) - base)      # two more references

del alias                                # remove one name
holder.clear()                           # remove the dict's reference
print(sys.getrefcount(data) - base)      # back to where we started

class Node:
    def __init__(self, name):
        self.name = name
        self.partner = None

    def __del__(self):                   # runs when the object is destroyed
        print("freed", self.name)

solo = Node("solo")
del solo                                 # count hits zero: freed at once

a, b = Node("a"), Node("b")
a.partner, b.partner = b, a              # a cycle: each points to the other
del a, b                                 # counts do not reach zero
print("after del: nothing freed yet")

found = gc.collect()                     # the garbage collector finds the cycle
print("collector found objects:", found > 0)
print(gc.isenabled(), len(gc.get_threshold()))
```

```output
2
0
freed solo
after del: nothing freed yet
freed a
freed b
collector found objects: True
True 3
```

<Mistakes>

<Mistake title="Thinking del destroys the object">

<Wrong>

```python
a = [1, 2, 3]
b = a
del a
print(b)   # [1, 2, 3]
```

</Wrong>

<Right>

```python
a = [1, 2, 3]
b = a
del a
del b            # now no name points to the list, so it is freed
print("freed")
```

</Right>

`del` removes a **name**, not the object. The object is freed only when its last reference is gone.

</Mistake>

<Mistake title="Keeping big data alive in a global list">

<Wrong>

```python
cache = []

def handle(request):
    cache.append(request * 1000)   # grows forever: a memory leak
    return len(cache)

print(handle("x"), handle("y"))   # 1 2
```

</Wrong>

<Right>

```python
from collections import deque

cache = deque(maxlen=100)          # old items are dropped automatically

def handle(request):
    cache.append(request * 1000)
    return len(cache)

print(handle("x"), handle("y"))   # 1 2
```

</Right>

Python cannot free objects that are still referenced. A list that only grows is the most common memory leak. Give caches a size limit.

</Mistake>

<Mistake title="Loading everything into memory at once">

<Wrong>

```python
squares = [n * n for n in range(1000000)]   # one million numbers in memory
print(sum(squares) > 0)   # True
```

</Wrong>

<Right>

```python
squares = (n * n for n in range(1000000))   # one number at a time
print(sum(squares) > 0)   # True
```

</Right>

When you only need to loop once, a generator keeps memory use tiny.

</Mistake>

<InterviewQA>

<QA q="How does memory management work in Python?">

Python uses a **private heap** for all objects, managed by the interpreter. CPython frees memory mainly through **reference counting**: each object tracks how many references point to it and is deallocated the moment the count reaches zero. A **cyclic garbage collector** handles reference cycles that counting cannot free. Small objects are allocated from pools by a specialised allocator (pymalloc) for speed.

</QA>

<QA q="What is reference counting?">

A count stored in every object of how many references point to it. It increases on assignment, on being passed as an argument and on being stored in a container. It decreases when a reference is deleted, reassigned or goes out of scope. At zero, the object is destroyed immediately. You can inspect it with `sys.getrefcount()`.

</QA>

<QA q="Why does Python need a garbage collector if it has reference counting?">

Because of **reference cycles**. If object A refers to B and B refers to A, their counts never drop to zero, even after all outside references are gone. The `gc` module periodically detects groups of objects that are unreachable from the program and frees them.

</QA>

<QA q="What is generational garbage collection?">

The collector sorts objects into three generations by age. New objects start in generation 0, which is scanned most often. Objects that survive a collection move to an older generation, which is scanned less often. This is based on the observation that most objects die young, and it keeps collection cheap.

</QA>

<QA q="How can you reduce memory use in a Python program?">

Use generators and iterators for large data, process files line by line, prefer tuples to lists for fixed data, use `__slots__` in classes with many instances, delete or scope large temporary objects, and avoid unbounded global caches. Profile with `tracemalloc` to find what is using memory.

</QA>

<CheatSheet>

| Term | Meaning |
| --- | --- |
| Private heap | Where all Python objects live |
| Reference count | Number of references to an object |
| Count reaches 0 | Object is freed immediately |
| Reference cycle | Objects that point to each other |
| Garbage collector | Finds and frees unreachable cycles |
| Generations | 0 (young, checked often) to 2 (old) |
| `sys.getrefcount(x)` | See the count |
| `gc.collect()` | Run the collector now |
| `del x` | Remove the name `x` |
