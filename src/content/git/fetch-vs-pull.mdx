<Analogy>

**Fetch** is checking your letter box and reading the letters at the door. **Pull** is checking the letter box and immediately acting on every letter: filing them, paying the bills, replying.

Fetch lets you **look before you act**; pull acts straight away.

</Analogy>

## Simple explanation

| | `git fetch` | `git pull` |
| --- | --- | --- |
| Downloads new commits | yes | yes |
| Updates `origin/main` | yes | yes |
| Changes your branch | **no** | **yes** (merge or rebase) |
| Changes your files | no | yes |
| Can cause conflicts | no | yes |
| Safe any time | yes | best with a clean working directory |

`git pull` = `git fetch` + `git merge origin/<branch>` (or `git rebase` with `--rebase`).

Why fetch first? To see what is coming before it touches your work:

```bash
git fetch
git log --oneline main..origin/main     # commits on the remote that I do not have
git diff main origin/main               # what they change
git merge origin/main                   # or: git rebase origin/main
```

Other reasons to fetch:

- `git fetch --all --prune` before starting a day: all remotes updated, deleted branches cleaned up
- Check whether your branch is behind: `git status` after a fetch says "Your branch is behind 'origin/main' by 3 commits"
- Get a teammate's branch to review: `git fetch` then `git switch their-feature`

Use **pull** when you just want the latest and you trust it (for example on `main` before branching). Use **fetch** when you want control: reviewing, or deciding between merge and rebase.

## Code example

```bash
git fetch
git status
git log --oneline main..origin/main
git merge origin/main
```

<Mistakes>

<Mistake title="Running git pull on the wrong branch">

<Wrong>

```bash
# on feature-x
git pull origin main      # merges main into feature-x; maybe not what you wanted
```

</Wrong>

<Right>

```bash
git fetch
git rebase origin/main    # deliberately update feature-x on top of the latest main
```

</Right>

Fetch first, then choose how and where to integrate.

</Mistake>

<Mistake title="Believing fetch updated your files">

<Wrong>

```bash
git fetch
cat app.py                # "still old, fetch is broken"
```

</Wrong>

<Right>

```bash
git fetch
git merge origin/main     # now your branch and files update
```

</Right>

Fetch only updates `origin/*`. Your branch moves when you merge, rebase or pull.

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What is the difference between git fetch and git pull?">

`git fetch` downloads commits and updates remote-tracking branches such as origin/main without modifying local branches or the working directory. `git pull` does a fetch and then integrates the upstream branch into the current branch by merging (or rebasing with --rebase), which can change files and cause conflicts.

</QA>

<QA q="How do you see what changes a pull would bring before pulling?">

`git fetch`, then `git log main..origin/main` to list incoming commits and `git diff main origin/main` (or `...origin/main`) to see the changes, then merge or rebase when ready.

</QA>

<QA q="What does git fetch --prune do?">

It removes remote-tracking branches (such as origin/old-feature) whose branches were deleted on the remote, keeping `git branch -a` accurate.

</QA>

<CheatSheet>

| What you want | Command |
| --- | --- |
| Download only | `git fetch` |
| All remotes, clean up | `git fetch --all --prune` |
| Am I behind? | `git fetch` then `git status` |
| Incoming commits | `git log main..origin/main` |
| Incoming changes | `git diff main origin/main` |
| Integrate | `git merge origin/main` or `git rebase origin/main` |
| All in one | `git pull` / `git pull --rebase` |

</CheatSheet>
