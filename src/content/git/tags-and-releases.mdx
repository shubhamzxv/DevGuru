<Analogy>

A branch is like a bookmark you keep moving as you read. A **tag** is like a sticky note saying "Edition 2, printed March 2026" on one page: it never moves.

Tags mark **versions**, so you can always rebuild or roll back to exactly what was released.

</Analogy>

## Simple explanation

Two kinds of tag:

- **Annotated** (recommended for releases): stores the tagger, date and a message. `git tag -a v1.2.0 -m "Release 1.2.0"`
- **Lightweight**: just a name for a commit. `git tag v1.2.0`

Commands:

- `git tag` list tags; `git tag -l "v1.*"` filter
- `git tag -a v1.2.0 <commit>` tag an older commit
- `git show v1.2.0` details
- `git push origin v1.2.0` push one tag, `git push --tags` push all (tags are **not pushed by default**)
- `git switch --detach v1.2.0` look at the code of a release (detached HEAD)
- `git tag -d v1.2.0` and `git push origin --delete v1.2.0` delete

**Semantic versioning** (SemVer): `MAJOR.MINOR.PATCH`

- **PATCH** (1.2.**3**): bug fixes only
- **MINOR** (1.**3**.0): new features, backwards compatible
- **MAJOR** (**2**.0.0): breaking changes
- Pre-releases: `2.0.0-beta.1`

A **GitHub release** is built on a tag: a title, release notes (GitHub can generate them from merged PRs), and attached files (binaries, zips). Tags also commonly **trigger deployments**: a GitHub Actions workflow on `push: tags: ["v*"]` builds and publishes the release.

Never move or re-use a released tag: people and pipelines rely on `v1.2.0` meaning exactly one commit. Release a new version instead.

## Code example

```bash
git tag -a v1.0.0 -m "First public release"
git tag
git show v1.0.0 --no-patch
git push origin v1.0.0
gh release create v1.0.0 --generate-notes
```

```output
v1.0.0
tag v1.0.0
Tagger: Shubham Kumar <you@example.com>

https://github.com/you/shop/releases/tag/v1.0.0
```

<Mistakes>

<Mistake title="Forgetting to push tags">

<Wrong>

```bash
git tag -a v1.2.0 -m "Release"
git push                 # the tag stays on your laptop; the release pipeline never starts
```

</Wrong>

<Right>

```bash
git push origin v1.2.0   # or: git push --follow-tags
```

</Right>

`git push` sends branches, not tags, unless you ask.

</Mistake>

<Mistake title="Moving a released tag">

<Wrong>

```bash
git tag -f v1.2.0 && git push -f origin v1.2.0   # "fixing" a release in place
```

</Wrong>

<Right>

```bash
git tag -a v1.2.1 -m "Fix in release 1.2.1"
git push origin v1.2.1
```

</Right>

Others may already have deployed v1.2.0. Versions must be immutable.

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What is the difference between a tag and a branch?">

Both are references to commits. A branch moves forward as new commits are added; a tag is meant to stay fixed on one commit, typically to mark a release. Annotated tags also store a message, tagger and date.

</QA>

<QA q="What is semantic versioning?">

A version format MAJOR.MINOR.PATCH: increment PATCH for backwards-compatible bug fixes, MINOR for backwards-compatible new features, and MAJOR for breaking changes. Pre-release and build metadata can be appended (1.4.0-rc.1).

</QA>

<QA q="How are tags used in CI/CD?">

Pushing a tag such as v1.4.0 can trigger a pipeline that builds, tests, versions and publishes the artifact (container image, package) and creates a release with notes, so every deployed version maps to an exact commit.

</QA>

<CheatSheet>

| What you want | Command |
| --- | --- |
| Annotated tag | `git tag -a v1.2.0 -m "Release 1.2.0"` |
| Tag an old commit | `git tag -a v1.1.0 <id>` |
| List | `git tag` / `git tag -l "v1.*"` |
| Push one / all | `git push origin v1.2.0` / `git push --tags` |
| Look at a release | `git switch --detach v1.2.0` |
| Delete | `git tag -d v1.2.0` + `git push origin --delete v1.2.0` |
| GitHub release | `gh release create v1.2.0 --generate-notes` |
| SemVer | MAJOR.MINOR.PATCH |

</CheatSheet>
