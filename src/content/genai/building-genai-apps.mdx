<Analogy>

You hire a smart graduate. First you **explain the job clearly** (prompt). If they need company facts, you hand them the **policy binder to look things up** (RAG). If they must do things, you give them **access to the systems** (tools). Only if they still do not write in the company style after all that do you send them for **months of training** (fine-tuning).

</Analogy>

## Simple explanation

**Four ways to adapt a model**, from cheapest to costliest:

| Approach | What it changes | Use when | Cost / effort |
| --- | --- | --- | --- |
| **Prompt engineering** | the instructions | always first | lowest |
| **RAG** | adds your documents to the prompt at question time | answers need **your data** or **fresh** data | medium |
| **Tools / agents** | lets the model call your APIs | it must **look up live data** or **take actions** | medium |
| **Fine-tuning** | the model's weights | you need a fixed **style, format or skill**, or a smaller cheaper model for one task | highest |

A key interview line: **RAG gives the model knowledge. Fine-tuning changes its behaviour.** They can be combined.

**A typical GenAI backend**:

```text
User → your API → (guardrails) → build prompt (+ retrieved context) → LLM API
                                                  ↑                      ↓
                                        vector DB / tools        validate output → User
```

**Production concerns**:

| Concern | What to do |
| --- | --- |
| **Cost** | priced per **token** (input and output); use small models, shorter prompts, caching |
| **Latency** | **stream** the answer; smaller models; fewer LLM calls; cap output length |
| **Reliability** | timeouts, retries with backoff, fallback model, handle rate limits (429) |
| **Quality** | an **eval set** you run on every change |
| **Caching** | **prompt caching** for long repeated prefixes; response cache for identical questions |
| **Observability** | log prompt, output, tokens, latency, cost per request |
| **Security** | keep API keys on the server, never in the browser; guardrails |

**Streaming** sends tokens to the user as they are generated, so the first words appear in under a second even if the full answer takes ten.

## Code example

Estimating the monthly bill. Prices here are example numbers; check your provider's price page:

```python
def monthly_cost(requests_per_day, input_tokens, output_tokens, price_in, price_out):
    """Prices are per 1 million tokens."""
    per_request = input_tokens / 1e6 * price_in + output_tokens / 1e6 * price_out
    return per_request, per_request * requests_per_day * 30

plans = {
    "large model": (3.00, 15.00),
    "small model": (0.25, 1.25),
}
for name, (price_in, price_out) in plans.items():
    per_request, month = monthly_cost(10_000, input_tokens=2_000, output_tokens=300,
                                      price_in=price_in, price_out=price_out)
    print(f"{name}: ${per_request:.5f} per request, ${month:,.0f} per month")
```

```output
large model: $0.01050 per request, $3,150 per month
small model: $0.00087 per request, $262 per month
```

Retry with **exponential backoff** for rate limits and brief failures:

```python
import random

random.seed(4)
attempts_log = []

def flaky_llm_call():
    attempts_log.append(1)
    if len(attempts_log) < 3:
        raise TimeoutError("rate limited")
    return "answer"

def call_with_retry(fn, max_attempts=5, base_delay=1.0):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TimeoutError as e:
            delay = base_delay * 2 ** (attempt - 1) + random.uniform(0, 0.5)   # backoff + jitter
            print(f"attempt {attempt} failed ({e}); wait {delay:.1f}s")      # real code: time.sleep(delay)
    raise RuntimeError("gave up: use the fallback model")

print(call_with_retry(flaky_llm_call))
```

```output
attempt 1 failed (rate limited); wait 1.1s
attempt 2 failed (rate limited); wait 2.1s
answer
```

A response cache: the same question is answered once:

```python
import hashlib

cache = {}
calls = {"llm": 0}

def expensive_llm(prompt):
    calls["llm"] += 1
    return f"answer to: {prompt}"

def cached_llm(prompt):
    key = hashlib.sha256(prompt.strip().lower().encode()).hexdigest()
    if key not in cache:
        cache[key] = expensive_llm(prompt)
    return cache[key]

for q in ["What is your refund policy?", "what is your refund policy?  ", "Do you ship to Pune?"]:
    cached_llm(q)
print("questions: 3 | LLM calls:", calls["llm"])
```

```output
questions: 3 | LLM calls: 2
```

<Mistakes>

<Mistake title="Fine-tuning to add company knowledge">

<Wrong>

```text
"Our docs change weekly, so let's fine-tune the model on them every week."
```

</Wrong>

<Right>

```text
"Put the docs in a vector database and use RAG. Updating a document is just re-indexing it,
and answers can cite the source."
```

</Right>

Fine-tuning is slow to update and does not reliably store facts. RAG is the tool for knowledge.

</Mistake>

<Mistake title="Calling the LLM API from the browser">

<Wrong>

```javascript
fetch("https://api.llm-provider.com/v1/chat", { headers: { Authorization: "Bearer sk-live-..." } })
```

</Wrong>

<Right>

```text
Browser → your backend (auth, rate limit, guardrails) → LLM API with the key from an env variable
```

</Right>

Anything in frontend code is public. A leaked key means someone else spends your money.

</Mistake>

<InterviewQA>

<QA q="RAG vs fine-tuning: when do you use which?">

RAG when the model needs private, large or frequently changing knowledge and answers should cite sources; it changes the prompt, not the model. Fine-tuning when you need consistent style, format or task behaviour, or want a small model to match a large one on a narrow task. Start with prompting, add RAG for knowledge, fine-tune last; they can be combined.

</QA>

<QA q="How do you reduce the cost of an LLM feature?">

Use the smallest model that passes your evals, shorten prompts and retrieved context, cap output tokens, cache (prompt caching and response caching), batch non-urgent work, route easy requests to cheaper models, and monitor cost per request.

</QA>

<QA q="How do you reduce latency?">

Stream tokens to the user, use faster or smaller models, reduce output length, cut the number of sequential LLM calls (run independent calls in parallel), cache, and keep prompts short. Time to first token matters most for chat.

</QA>

<QA q="How do you make LLM calls reliable in production?">

Timeouts, retries with exponential backoff and jitter, handling 429 rate limits, a fallback model or provider, idempotent requests, output validation with a repair retry, circuit breakers, and queues for background work.

</QA>

<CheatSheet>

| Need | Do |
| --- | --- |
| Better answers, same model | improve the prompt, add examples |
| Your / fresh knowledge | **RAG** |
| Live data or actions | **tools / agents** |
| Fixed style or narrow skill | **fine-tune** |
| Lower cost | small model, short prompts, caching, max tokens |
| Lower latency | streaming, parallel calls, small model |
| Reliability | timeout, retry + backoff, fallback |
| Quality control | eval set on every change |
| Security | key on server, guardrails, validate output |
| Visibility | log tokens, cost, latency per request |

</CheatSheet>
