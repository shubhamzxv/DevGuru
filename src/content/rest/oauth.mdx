<Analogy>

A hotel gives a valet a **valet key**: it starts the car and drives it a short distance, but cannot open the boot or the glovebox. You never hand over your house keys, and you can take the valet key back any time.

**OAuth** gives apps a valet key to your account: "this photo printing app may **read** my Google Photos for one hour", without ever seeing your Google password.

</Analogy>

## Simple explanation

OAuth 2.0 is a standard for **delegated authorization**. The roles:

- **Resource owner**: you, the user
- **Client**: the app that wants access (a photo printing app)
- **Authorization server**: issues tokens after you log in and agree (Google's login page)
- **Resource server**: the API holding your data (Google Photos API)

The **Authorization Code flow** (used by websites and, with PKCE, by mobile and single-page apps):

1. The app sends you to the authorization server: `https://accounts.google.com/o/oauth2/auth?client_id=...&redirect_uri=...&scope=photos.read&state=xyz&code_challenge=...`
2. You log in **on Google's page** (the app never sees your password) and approve the **scopes** it asked for
3. Google redirects back to the app's `redirect_uri` with a short-lived **authorization code**
4. The app's backend exchanges the code (plus its client secret, or the PKCE verifier) for an **access token**, and often a **refresh token**
5. The app calls the API with `Authorization: Bearer <access token>`

Other parts to know:

- **Scopes** limit what the token may do (`photos.read`, not `photos.delete`)
- **state** is a random value checked on return, to stop CSRF attacks on the login flow
- **PKCE** (Proof Key for Code Exchange) protects apps that cannot keep a secret (mobile, SPA): the app proves it is the same one that started the flow
- **Client Credentials flow**: machine-to-machine, no user; the service gets a token with its own id and secret
- **OpenID Connect (OIDC)** is a layer on top of OAuth for **login**: it adds an **ID token** (a JWT) saying who the user is. "Sign in with Google" is OIDC
- The old **Implicit** and **Password** flows are deprecated; do not use them in new apps

Remember: OAuth is about **authorization** (what an app may do); OIDC adds **authentication** (who the user is).

## Code example

Step 4, exchanging the code for tokens on your backend (server-to-server):

```python
import requests

def exchange_code(code: str, verifier: str) -> dict:
    resp = requests.post(
        "https://oauth2.googleapis.com/token",
        data={
            "grant_type": "authorization_code",
            "code": code,                                  # from the redirect, valid ~1 minute
            "redirect_uri": "https://devguru.dev/auth/callback",
            "client_id": "1234.apps.googleusercontent.com",
            "client_secret": "from-env-not-from-code",
            "code_verifier": verifier,                     # PKCE
        },
        timeout=5,
    )
    resp.raise_for_status()
    return resp.json()
```

Client Credentials, for one service calling another:

```python
token = requests.post(
    "https://auth.example.com/oauth2/token",
    data={"grant_type": "client_credentials", "scope": "orders:read"},
    auth=("billing-service", "client-secret-from-env"),    # the service's own credentials
    timeout=5,
).json()["access_token"]

orders = requests.get("https://api.example.com/orders", headers={"Authorization": f"Bearer {token}"}, timeout=5)
```

<Mistakes>

<Mistake title="Asking users for their password on another site">

<Wrong>

```text
"Enter your Gmail password here so we can import your contacts."
```

</Wrong>

<Right>

```text
Redirect to Google with scope=contacts.readonly; receive a token; never see the password.
```

</Right>

Collecting other services' passwords is exactly what OAuth exists to prevent, and the user cannot limit or revoke access.

</Mistake>

<Mistake title="Not checking the state parameter">

<Wrong>

```python
@app.get("/auth/callback")
def callback(code: str):
    return exchange_code(code, verifier)       # accepts any code, even one an attacker sent
```

</Wrong>

<Right>

```python
@app.get("/auth/callback")
def callback(code: str, state: str, request: Request):
    if state != request.session.pop("oauth_state", None):
        raise HTTPException(400, "Invalid state")
    return exchange_code(code, request.session.pop("pkce_verifier"))
```

</Right>

`state` ties the callback to the login you started, preventing login CSRF.

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What is OAuth 2.0?">

An authorization framework that lets a user grant a third-party application limited, revocable access to their resources on another service without sharing credentials. An authorization server issues access tokens with specific scopes, which the client presents to the resource server.

</QA>

<QA q="Explain the authorization code flow with PKCE.">

The client creates a random code verifier and sends its hash (the code challenge) when redirecting the user to the authorization server. The user authenticates and consents; the server redirects back with an authorization code. The client exchanges the code plus the original verifier at the token endpoint; the server checks the verifier matches the challenge and returns access (and refresh) tokens. PKCE stops intercepted codes from being used.

</QA>

<QA q="What is the difference between OAuth 2.0 and OpenID Connect?">

OAuth 2.0 handles authorization: granting access to resources through access tokens. OpenID Connect adds authentication on top: an ID token (a JWT) with the user's identity, a userinfo endpoint and standard scopes such as openid, profile and email. "Sign in with Google" uses OIDC.

</QA>

<QA q="Which OAuth flow do services use to call each other?">

The Client Credentials grant: a service authenticates with its own client id and secret (or a certificate) at the token endpoint and receives an access token for its own permissions. There is no user involved.

</QA>

<CheatSheet>

| Term | Meaning |
| --- | --- |
| Resource owner | the user |
| Client | the app asking for access |
| Authorization server | issues codes and tokens |
| Resource server | the API with the data |
| Scope | what the token may do |
| Authorization code + PKCE | flow for web, mobile, SPA |
| Client credentials | service-to-service, no user |
| Refresh token | gets new access tokens |
| state | anti-CSRF check on the callback |
| OIDC / ID token | login: who the user is |

</CheatSheet>
