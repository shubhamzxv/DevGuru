title: select_related vs prefetch_related (N+1 problem)
summary: The N+1 problem is one query for a list plus one more query per row for its related object; select_related fixes it for ForeignKey and OneToOne with a SQL JOIN, and prefetch_related fixes it for reverse and ManyToMany relations with one extra query per relation.

---

<Analogy>

A teacher checking 30 students' parents' phone numbers. **N+1**: open the class list, then walk to the office 30 times, once per student. **select_related**: get one combined sheet with student and parent on the same line (JOIN). **prefetch_related**: get the class list, then one trip to fetch all 30 parent records at once and match them up.

</Analogy>

## Simple explanation

The problem:

```python
for product in Product.objects.all():          # 1 query
    print(product.category.name)               # +1 query PER product → N+1
```

**select_related**: for **forward ForeignKey and OneToOne** (the "one" side). One query with a JOIN:

```python
for product in Product.objects.select_related("category"):    # 1 query total
    print(product.category.name)
```

**prefetch_related**: for **reverse ForeignKey and ManyToMany** (the "many" side). One extra query per relation, joined in Python:

```python
for order in Order.objects.prefetch_related("items__product"):   # 3 queries total
    for item in order.items.all():
        print(item.product.name)
```

| | `select_related` | `prefetch_related` |
| --- | --- | --- |
| Relations | ForeignKey, OneToOne (forward) | reverse FK (`items`), ManyToMany (`tags`), GenericFK |
| How | SQL JOIN, one query | separate `WHERE id IN (...)` query, joined in Python |
| Combine | yes: `select_related("customer").prefetch_related("items__product")` | |

**Prefetch** objects customise the prefetch query:

```python
from django.db.models import Prefetch
Order.objects.prefetch_related(
    Prefetch("items", queryset=OrderItem.objects.select_related("product").filter(quantity__gt=1), to_attr="big_items")
)
```

Find N+1 problems with **django-debug-toolbar** (shows query count per page), `assertNumQueries` in tests, or logging. In DRF, nested serializers are the classic source: put `select_related`/`prefetch_related` in the view's `get_queryset()`.

Other query-size tools: `only("id", "name")` / `defer("description")` (fewer columns), `values()` (no model objects), `iterator()` (stream big results).

## Code example

```python
from django.db import connection
from django.test.utils import CaptureQueriesContext

with CaptureQueriesContext(connection) as ctx:
    for prod in Product.objects.all():
        _ = prod.category.name
print("no select_related:", len(ctx))

with CaptureQueriesContext(connection) as ctx:
    for prod in Product.objects.select_related("category"):
        _ = prod.category.name
print("select_related('category'):", len(ctx))

with CaptureQueriesContext(connection) as ctx:
    for o in Order.objects.all():
        _ = [i.product.name for i in o.items.all()]
print("orders → items → product, no prefetch:", len(ctx))

with CaptureQueriesContext(connection) as ctx:
    for o in Order.objects.select_related("customer").prefetch_related("items__product"):
        _ = o.customer.username, [i.product.name for i in o.items.all()]
print("select_related + prefetch_related:", len(ctx))
```

```output
no select_related: 8
select_related('category'): 1
orders → items → product, no prefetch: 9
select_related + prefetch_related: 3
```

7 products → 1 + 7 = 8 queries become 1. With 10,000 products it would be 10,001 queries vs 1.

SELECT p.name, c.name AS category FROM product p JOIN category c ON c.id = p.category_id;

SELECT id, name, category_id FROM product;
SELECT id, name FROM category WHERE id IN (1, 2, 3);

<Mistakes>

<Mistake title="prefetch_related for a ForeignKey you only read">

<Wrong>

```python
Product.objects.prefetch_related("category")     # works, but 2 queries instead of 1
```

</Wrong>

<Right>

```python
Product.objects.select_related("category")
```

</Right>

</Mistake>

<Mistake title="Filtering after prefetch throws the prefetch away">

<Wrong>

```python
for order in Order.objects.prefetch_related("items"):
    big = order.items.filter(quantity__gt=1)     # a NEW query per order: N+1 again
```

</Wrong>

<Right>

```python
Order.objects.prefetch_related(Prefetch("items", queryset=OrderItem.objects.filter(quantity__gt=1), to_attr="big_items"))
# then use order.big_items
```

</Right>

</Mistake>

<InterviewQA>

<QA q="What is the N+1 query problem?">

Fetching a list with one query and then accessing a related object for each item, which lazily triggers one additional query per item: N+1 queries in total. It is invisible in code but makes pages and APIs slow as data grows.

</QA>

<QA q="What is the difference between select_related and prefetch_related?">

select_related follows forward ForeignKey and OneToOne relations using a SQL JOIN in the same query. prefetch_related handles reverse ForeignKey and ManyToMany relations by running a separate query per relation (`WHERE id IN (...)`) and joining the results in Python. Both can be combined and chained across relations with double underscores.

</QA>

<QA q="How do you detect N+1 queries?">

django-debug-toolbar or Silk in development to see query counts and duplicates, `assertNumQueries` in tests to lock the count, logging of `django.db.backends`, and APM tools in production; then fix with select_related, prefetch_related, Prefetch objects or annotations.

</QA>

<CheatSheet>

| Relation | Use | Queries |
| --- | --- | --- |
| `product.category` (FK) | `select_related("category")` | 1 (JOIN) |
| `user.profile` (OneToOne) | `select_related("profile")` | 1 |
| `order.items` (reverse FK) | `prefetch_related("items")` | 2 |
| `product.tags` (M2M) | `prefetch_related("tags")` | 2 |
| Deep | `prefetch_related("items__product")` | 3 |
| Custom | `Prefetch("items", queryset=..., to_attr=...)` | |
| Lock in tests | `with self.assertNumQueries(3):` | |
