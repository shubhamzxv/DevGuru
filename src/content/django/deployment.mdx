<Analogy>

Moving a home kitchen into a restaurant: you need several cooks working at once (**Gunicorn workers**), a front desk that greets guests and hands out the menu cards directly (**Nginx**: HTTPS and static files), the recipe secrets kept in a locked drawer (**environment variables**), and the pantry in a proper store room (**RDS**), not under the sink.

</Analogy>

## Simple explanation

```text
Browser ─HTTPS─> Nginx / ALB ──> Gunicorn (3–9 workers) ──> Django ──> PostgreSQL (RDS)
                   │                                          └──> Redis (cache, Celery broker)
                   └── /static/  served directly (or S3 + CloudFront)
```

**1. Settings from the environment** (`DEBUG=False`, `SECRET_KEY`, `ALLOWED_HOSTS`, `DATABASE_URL`, secure cookies): see Settings and Security.

**2. Gunicorn**

```bash
pip install gunicorn
gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 3 --timeout 60 --access-logfile -
```

Workers ≈ `2 × CPU cores + 1`. For async views or websockets: `uvicorn config.asgi:application` or Gunicorn with Uvicorn workers.

**3. Static files**

```bash
python manage.py collectstatic --noinput
```

**4. Nginx** in front:

```text
server {
    listen 80;
    server_name shop.example.com;
    location /static/ { alias /home/deploy/shop/staticfiles/; }
    location /media/  { alias /home/deploy/shop/media/; }
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

HTTPS with Let's Encrypt (`certbot --nginx`) or at the AWS load balancer (ACM certificate).

**5. Keep it running**: a systemd unit for Gunicorn (`Restart=always`, see Linux → Services), or a container with a restart policy / orchestrator.

**6. Deploy steps**, in order: pull code / new image → install requirements → `migrate` (once) → `collectstatic` → restart Gunicorn (graceful: `systemctl reload` sends HUP) → health check.

**Where on AWS**

| Option | Notes |
| --- | --- |
| EC2 + Nginx + Gunicorn + systemd | classic, full control |
| **ECS Fargate** + ALB (Docker image) | containers, autoscaling, workers as a second service |
| Elastic Beanstalk | managed EC2 with Django platform |
| App Runner | simplest container hosting |
| Database | **RDS PostgreSQL** (Multi-AZ, backups), media on **S3**, Redis on **ElastiCache**, secrets in **Secrets Manager** |

## Code example

```bash
DJANGO_SETTINGS_MODULE=config.settings.prod python manage.py check --deploy
python manage.py migrate --noinput
python manage.py collectstatic --noinput
gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 3
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/products/health/
```

<Mistakes>

<Mistake title="runserver or DEBUG=True in production">

<Wrong>

```bash
DEBUG=True python manage.py runserver 0.0.0.0:80
```

</Wrong>

<Right>

```bash
gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 3    # behind nginx, DEBUG=False
```

</Right>

</Mistake>

<Mistake title="Missing proxy headers behind a load balancer">

<Wrong>

```text
SECURE_SSL_REDIRECT=True behind an ALB that talks HTTP to the app → infinite redirect loop;
request.is_secure() is always False.
```

</Wrong>

<Right>

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
USE_X_FORWARDED_HOST = True   # if the proxy sets it
```

</Right>

</Mistake>

<InterviewQA>

<QA q="How do you deploy a Django application?">

Configure production settings from environment variables (DEBUG off, secrets, allowed hosts, secure cookies), run it with Gunicorn (or Uvicorn for ASGI) managed by systemd or a container platform, put Nginx or a load balancer in front for HTTPS and static files, collect static files to Nginx/WhiteNoise/S3, use a managed database like RDS, run migrations as a deploy step, and add logging, monitoring and health checks.

</QA>

<QA q="Why put Nginx in front of Gunicorn?">

Nginx efficiently handles many slow client connections, TLS termination, buffering, compression, serving static and media files and simple rate limiting, so Gunicorn workers spend their time only on Python requests; Gunicorn is not designed to face the internet directly.

</QA>

<QA q="How many Gunicorn workers should you run?">

A common starting point is 2 × CPU cores + 1 sync workers, then tune by measuring memory per worker and latency; I/O-heavy apps may use threads (gthread) or async workers, and in containers the orchestrator can scale replicas instead of adding workers.

</QA>

| Step | Command / setting |
| --- | --- |
| Check | `python manage.py check --deploy` |

| Proxy | Nginx `proxy_pass` + `X-Forwarded-Proto` |
