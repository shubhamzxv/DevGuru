<Analogy>

A bank with **branches in different cities** (Regions). In each city it has **several buildings** a few kilometres apart, each with its own power and staff (Availability Zones). If one building floods, the other buildings in that city keep serving customers. Small **ATM kiosks** everywhere (edge locations) hand out cash quickly near where people are.

</Analogy>

## Simple explanation

| Term | What | Example |
| --- | --- | --- |
| **Region** | a geographic area with its own independent set of data centres | `ap-south-1` Mumbai, `ap-south-2` Hyderabad, `us-east-1` N. Virginia, `eu-west-1` Ireland |
| **Availability Zone (AZ)** | one or more data centres in a Region with separate power, cooling and networking, connected by fast private links | `ap-south-1a`, `ap-south-1b`, `ap-south-1c` |
| **Edge location** | small sites for CloudFront, Route 53, Global Accelerator | hundreds of cities worldwide |
| **Local Zone / Wavelength** | extensions closer to users or 5G networks | low-latency use cases |

**Choosing a Region**: (1) **data residency / law** (customer data stays in India), (2) **latency** to users (Mumbai for Indian users), (3) **service availability** (new services launch in some Regions first, often us-east-1), (4) **price** (differs by Region).

**Scope of services**

| Scope | Services |
| --- | --- |
| Global | IAM, Route 53, CloudFront, Organizations |
| Regional | S3 buckets (names are global), VPC, Lambda, DynamoDB, SQS, load balancers |
| Per AZ | EC2 instances, EBS volumes, subnets |

**High availability**: put resources in **at least two AZs**: subnets in 1a and 1b, an Auto Scaling group across both, a load balancer spanning both, RDS **Multi-AZ** (a standby in another AZ). One AZ can fail without the application going down. **Disaster recovery** across Regions (backups or a standby stack in another Region) protects against a whole Region failing.

Data transfer between AZs costs a little; between Regions more; into AWS is free; out to the internet is charged.

## Code example

```python
import boto3

ec2 = boto3.client("ec2", region_name="ap-south-1")
print([r["RegionName"] for r in ec2.describe_regions()["Regions"]][:6], "...")
print([z["ZoneName"] for z in ec2.describe_availability_zones()["AvailabilityZones"]])
```

```output
['af-south-1', 'ap-east-1', 'ap-east-2', 'ap-northeast-1', 'ap-northeast-2', 'ap-northeast-3'] ...
['ap-south-1a', 'ap-south-1b', 'ap-south-1c']
```

```bash
aws configure set region ap-south-1          # default Region for the CLI
aws s3 ls --region us-east-1                  # or per command
```

<Mistakes>

<Mistake title="Everything in one AZ">

<Wrong>

```text
Two EC2 instances "for high availability", both in ap-south-1a, and a Single-AZ RDS: one AZ outage = full outage.
```

</Wrong>

<Right>

```text
Subnets in 1a and 1b, the Auto Scaling group across both, ALB in both, RDS Multi-AZ.
```

</Right>

</Mistake>

<Mistake title="Creating resources in the wrong Region">

<Wrong>

```text
"My EC2 instance disappeared!" — the console was switched to us-east-1; the instance is in ap-south-1.
```

</Wrong>

<Right>

```text
Check the Region selector / --region / AWS_DEFAULT_REGION; tag resources; use one default Region per project.
```

</Right>

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What is the difference between a Region and an Availability Zone?">

A Region is a separate geographic area (for example ap-south-1 Mumbai) containing multiple Availability Zones. An AZ is one or more physically separate data centres within that Region with independent power, cooling and networking, linked by low-latency connections. Regions isolate failures and data geographically; AZs give high availability within a Region.

</QA>

<QA q="How do you make an application highly available on AWS?">

Deploy across at least two AZs: subnets in each, an Auto Scaling group spanning them behind a load balancer with health checks, Multi-AZ managed databases and caches, stateless app servers with sessions in Redis or DynamoDB, and S3 for files. For disaster recovery add backups or a standby in a second Region.

</QA>

<QA q="How do you choose an AWS Region?">

By data residency and compliance requirements, latency to users, availability of the services you need, and price; sometimes also by where your other systems or partners run.

</QA>
