<Analogy>

Hiring a **building management company** for your database. You still decide the rooms and furniture (schema, queries, indexes), but they handle the plumbing: nightly backups, security patches, a standby building ready if the main one floods (**Multi-AZ**), and extra reading rooms for visitors (**read replicas**).

</Analogy>

## Simple explanation

**What AWS manages vs what you manage**

| AWS | You |
| --- | --- |
| hardware, OS, DB installation | schema, indexes, queries |
| patching (in your maintenance window) | choosing size and storage |
| automated backups + point-in-time restore | connection handling, pooling |
| Multi-AZ failover | security groups, users, parameters |
| monitoring metrics | migrations, upgrade testing |

**High availability vs scaling**

| Feature | Purpose | How |
| --- | --- | --- |
| **Multi-AZ** | survive an AZ / instance failure | synchronous standby in another AZ, same endpoint, automatic failover (~1–2 min); the standby is not readable (Multi-AZ **cluster** has 2 readable standbys) |
| **Read replicas** | scale reads, reporting, cross-Region DR | asynchronous copies with their own endpoints (replication lag); can be promoted |
| **Backups** | recover from mistakes | automated daily snapshots + transaction logs, retention 1–35 days, **point-in-time restore** to a new instance; manual snapshots kept until deleted |

**Aurora**: MySQL/PostgreSQL compatible, storage spread over 3 AZs (6 copies), up to 15 low-lag replicas, cluster **writer** and **reader** endpoints, fast failover, Aurora Serverless v2 (scales capacity automatically), Global Database for multi-Region.

**Good practice**

- Private subnets (DB subnet group), security group allowing 5432 only from the app's SG
- Credentials in **Secrets Manager** (rotation) or IAM database authentication
- Encryption at rest (KMS) chosen at creation; TLS in transit
- **RDS Proxy** to pool connections (Lambda, many workers)
- Performance Insights to find slow queries; alarms on CPU, free storage, connections, replica lag
- Storage autoscaling; Graviton instance classes (`db.t4g`, `db.r7g`) are cheaper

## Code example

```python
import boto3

rds = boto3.client("rds", region_name="ap-south-1")
db = rds.create_db_instance(
    DBInstanceIdentifier="shop-db", Engine="postgres", DBInstanceClass="db.t4g.micro",
    AllocatedStorage=20, MasterUsername="shop", ManageMasterUserPassword=True,   # password in Secrets Manager
    MultiAZ=True, BackupRetentionPeriod=7, StorageEncrypted=True,
    DBSubnetGroupName="shop-private", VpcSecurityGroupIds=["sg-db"], PubliclyAccessible=False,
)["DBInstance"]
print("rds:", db["DBInstanceIdentifier"], db["Engine"], db["DBInstanceClass"], "MultiAZ", db["MultiAZ"], "backups", db["BackupRetentionPeriod"])

d = rds.describe_db_instances(DBInstanceIdentifier="shop-db")["DBInstances"][0]
print("endpoint:", d["Endpoint"]["Address"], d["Endpoint"]["Port"])

rr = rds.create_db_instance_read_replica(DBInstanceIdentifier="shop-db-replica", SourceDBInstanceIdentifier="shop-db")["DBInstance"]
print("replica of:", rr["ReadReplicaSourceDBInstanceIdentifier"])
```

```output

replica of: shop-db
```

<Mistakes>

<Mistake title="Thinking Multi-AZ is a read scaler or a backup">

<Wrong>

```text
"We have Multi-AZ, so we don't need backups, and the standby will serve our reports."
```

</Wrong>

<Right>

```text
Multi-AZ = availability. Read replicas = read scaling. Backups/PITR = recovery from mistakes.
```

</Right>

</Mistake>

<Mistake title="A public database">

<Wrong>

```text
PubliclyAccessible=True and 5432 open to 0.0.0.0/0 so developers can connect from home.
```

</Wrong>

<Right>

```text
Private subnets, SG from the app only; developers use SSM port forwarding through a bastion or a VPN.
```

</Right>

</Mistake>

<InterviewQA>

<QA q="What is the difference between Multi-AZ and read replicas?">

Multi-AZ keeps a synchronous standby in another AZ for high availability; it fails over automatically behind the same endpoint and (in the classic setup) serves no traffic. Read replicas are asynchronous copies with their own endpoints used to offload reads or for cross-Region disaster recovery; they can lag and must be promoted manually.

</QA>

<QA q="How do you restore an RDS database to a point before a bad change?">

Use point-in-time recovery, which replays transaction logs on top of the automated backups to create a new DB instance at any second within the retention period; then repoint the application or copy the needed data back. Manual snapshots can also be restored.

</QA>

<QA q="When would you choose Aurora over standard RDS PostgreSQL?">

When you need faster failover, more read replicas with low lag, storage that grows automatically and is replicated six ways across three AZs, serverless capacity scaling or a global database. Standard RDS can be cheaper and simpler for small or steady workloads and supports more engines.

</QA>

<CheatSheet>

| Need | Feature |
| --- | --- |
| HA | Multi-AZ (same endpoint, auto failover) |
| Read scaling / DR Region | read replicas |
| Undo mistakes | automated backups + PITR (1–35 days) · manual snapshots |
| Connections from Lambda | RDS Proxy |
| Secrets | `ManageMasterUserPassword` (Secrets Manager) · IAM auth |
| Network | private DB subnet group · SG from app SG |
| Cloud-native | Aurora: 6 copies / 3 AZs · writer + reader endpoints · Serverless v2 |
| Slow queries | Performance Insights |

</CheatSheet>
