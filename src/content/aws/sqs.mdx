<Analogy>

A **token counter at a busy clinic**. The receptionist (producer) hands out tokens and the patients wait in the queue; doctors (consumers) call the next token when they are free. If a doctor takes a token and leaves without treating the patient, the token goes back to the queue after a while (**visibility timeout**). A patient whose case keeps failing three times is sent to a **special desk** (dead-letter queue).

</Analogy>

## Simple explanation

**Why a queue?** The web request should not wait for slow work (emails, invoices, image processing, calling a slow partner API). Put a message on a queue, return quickly; workers process at their own pace. Spikes are absorbed; if workers crash, messages wait.

**The message lifecycle**

1. `SendMessage` (up to 256 KB; store big payloads in S3 and send the key)
2. `ReceiveMessage` (long polling `WaitTimeSeconds=20`, up to 10 messages)
3. Message becomes **invisible** for the **visibility timeout** (default 30 s)
4. Success → `DeleteMessage`. Failure/crash → it becomes visible again and is retried
5. After `maxReceiveCount` receives → moved to the **dead-letter queue (DLQ)**

| | **Standard** | **FIFO** (`.fifo`) |
| --- | --- | --- |
| Throughput | nearly unlimited | high, with limits per group |
| Delivery | **at least once** (rare duplicates) | **exactly once** processing (5-min dedup window) |
| Order | best effort | strict within a **MessageGroupId** |
| Use | most jobs | payments, order state changes |

**Other settings**: message retention (default 4 days, up to 14), delay queues, `ChangeMessageVisibility` for long jobs, SSE encryption, access policy (to let SNS/EventBridge send). **Lambda** can consume SQS directly (batches, partial batch failures, scales with queue depth). Celery can use SQS as its broker.

**Rules for consumers**: make processing **idempotent** (duplicates happen), set the visibility timeout longer than processing time (≈ 6× Lambda timeout), always configure a DLQ and alarm on it.

## Code example

```python
import boto3, json

sqs = boto3.client("sqs", region_name="ap-south-1")
dlq = sqs.create_queue(QueueName="orders-dlq")["QueueUrl"]
dlq_arn = sqs.get_queue_attributes(QueueUrl=dlq, AttributeNames=["QueueArn"])["Attributes"]["QueueArn"]
q = sqs.create_queue(QueueName="orders", Attributes={"VisibilityTimeout": "30",
        "RedrivePolicy": json.dumps({"deadLetterTargetArn": dlq_arn, "maxReceiveCount": "3"})})["QueueUrl"]

sqs.send_message(QueueUrl=q, MessageBody=json.dumps({"order_id": 4, "total": 848}))
m = sqs.receive_message(QueueUrl=q, MaxNumberOfMessages=10, WaitTimeSeconds=20)["Messages"][0]
print("received:", m["Body"])
print("while invisible:", len(sqs.receive_message(QueueUrl=q, WaitTimeSeconds=0).get("Messages", [])))
sqs.delete_message(QueueUrl=q, ReceiptHandle=m["ReceiptHandle"])           # done
print("after delete:", sqs.get_queue_attributes(QueueUrl=q, AttributeNames=["ApproximateNumberOfMessages"])["Attributes"])

# A poison message that always fails (visibility timeout 0 to see retries quickly)
sqs.set_queue_attributes(QueueUrl=q, Attributes={"VisibilityTimeout": "0"})
sqs.send_message(QueueUrl=q, MessageBody="bad json")
for i in range(4):
    print("attempt", i + 1, "got", len(sqs.receive_message(QueueUrl=q).get("Messages", [])))   # never deleted
print("dlq:", [x["Body"] for x in sqs.receive_message(QueueUrl=dlq).get("Messages", [])])

fq = sqs.create_queue(QueueName="payments.fifo", Attributes={"FifoQueue": "true", "ContentBasedDeduplication": "true"})["QueueUrl"]
for body in ["pay 1", "pay 1", "refund 1"]:
    sqs.send_message(QueueUrl=fq, MessageBody=body, MessageGroupId="order-4")
print("fifo:", [x["Body"] for x in sqs.receive_message(QueueUrl=fq, MaxNumberOfMessages=10)["Messages"]])
```

```output
received: {"order_id": 4, "total": 848}
while invisible: 0
after delete: {'ApproximateNumberOfMessages': '0'}
attempt 1 got 1
attempt 2 got 1
attempt 3 got 1
attempt 4 got 0
dlq: ['bad json']
fifo: ['pay 1', 'refund 1']
```

(Run against a mock of AWS.) After 3 failed receives the message moved to the DLQ; the FIFO queue dropped the duplicate "pay 1" and kept the order.

<Mistakes>

<Mistake title="Deleting before processing">

<Wrong>

```python
m = receive()
sqs.delete_message(...)        # deleted first
send_invoice(m)                # crashes → the order never gets an invoice
```

</Wrong>

<Right>

```python
m = receive()
send_invoice(m)                # idempotent
sqs.delete_message(...)        # only after success
```

</Right>

</Mistake>

<Mistake title="Visibility timeout shorter than the work">

<Wrong>

```text
Processing takes 90 s, visibility timeout 30 s → a second worker picks up the same message: duplicates.
```

</Wrong>

<Right>

```text
Timeout comfortably above processing time (or extend with ChangeMessageVisibility); 6× the Lambda timeout for Lambda.
```

</Right>

</Mistake>

<InterviewQA>

<QA q="What is the visibility timeout in SQS?">

The period after a consumer receives a message during which the message is hidden from other consumers. If the consumer deletes it in time, it is gone; if not (crash, error), it becomes visible again for retry. It should exceed the processing time and can be extended per message.

</QA>

<QA q="What is the difference between SQS standard and FIFO queues?">

Standard queues offer nearly unlimited throughput with at-least-once delivery and best-effort ordering, so consumers must handle duplicates and out-of-order messages. FIFO queues guarantee ordering within a message group and exactly-once processing via deduplication, with lower throughput limits.

</QA>

<QA q="Why use a dead-letter queue?">

To isolate messages that repeatedly fail (after maxReceiveCount) so they do not block or keep consuming workers, to keep them for investigation, and to redrive them after a fix. Alarm on DLQ depth.

</QA>

<CheatSheet>

| Step / setting | Remember |
| --- | --- |
| Send | `send_message` (≤ 256 KB; big data → S3 key) |
| Receive | long polling `WaitTimeSeconds=20`, up to 10 |
| Done | `delete_message(ReceiptHandle)` after success |
| Visibility timeout | > processing time · extend with `change_message_visibility` |
| Retries → DLQ | `RedrivePolicy` with `maxReceiveCount` |
| FIFO | `.fifo` · MessageGroupId · dedup id / content-based |
| Retention | 4 days default, up to 14 |
| Consumers | Lambda (batches) · Celery · ECS workers scaled on depth |
| Rule | idempotent processing |

</CheatSheet>
