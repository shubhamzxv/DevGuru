summary: A classic three-tier web app on AWS has a presentation tier (CloudFront and an ALB in public subnets), an application tier (stateless ECS/Fargate tasks or EC2 in an Auto Scaling group in private subnets) and a data tier (RDS Multi-AZ, ElastiCache, S3), spread over two or more AZs, secured with chained security groups and IAM roles, and monitored with CloudWatch.

<Analogy>

A **restaurant**: the **front of house** (tier 1) greets guests and takes orders; the **kitchen** (tier 2) cooks — any cook can make any dish, and more cooks join on busy nights; the **cold store and pantry** (tier 3) keep the ingredients safe, and only the kitchen may enter. Guests never walk into the kitchen or the store.

</Analogy>

## Simple explanation

| Tier | AWS services | Subnets | Security group rule |
| --- | --- | --- | --- |
| **1. Presentation / edge** | Route 53, CloudFront (+ WAF) for the React app and `/api/*`, ALB with ACM | public | ALB: 443 from internet / CloudFront prefix list |
| **2. Application** | ECS Fargate service (or EC2 ASG) running Django/FastAPI; Celery workers; SQS | private app | app: 8000 from ALB SG |
| **3. Data** | RDS PostgreSQL Multi-AZ, ElastiCache Redis, S3 (via gateway endpoint) | private data | DB: 5432 from app SG · cache: 6379 from app SG |

**Cross-cutting**

| Concern | How |
| --- | --- |
| High availability | everything in ≥ 2 AZs: ALB, tasks, NAT gateways, RDS Multi-AZ, Redis replica |
| Scaling | ECS service autoscaling on CPU / request count; read replicas; caching |
| Stateless app | sessions in Redis, files in S3, no local state |
| Secrets | Secrets Manager / SSM Parameter Store injected into tasks |
| Identity | task roles with least privilege; no access keys |
| Deploy | CI builds image → ECR → rolling or blue/green ECS deploy; migrations as a one-off task |
| Observability | CloudWatch logs/metrics/alarms, X-Ray, ALB access logs |
| Backups/DR | RDS automated backups + snapshots copied to another Region, S3 versioning, IaC to rebuild |
| Cost | Fargate Spot for workers, Graviton, Savings Plans, right-sizing, S3 endpoints instead of NAT |

**Request path**: user → Route 53 → CloudFront → (static from S3) or `/api/*` → ALB → Fargate task → Redis (cache hit?) → RDS → response.

**Why tiers?** Each tier scales and fails independently, security is layered (the database is unreachable from the internet), and teams can change one tier without touching the others.

## Code example

After a deploy, check every tier is healthy:

```bash
aws elbv2 describe-target-health --target-group-arn "$TG_ARN" \
  --query "TargetHealthDescriptions[].{ip:Target.Id,az:Target.AvailabilityZone,state:TargetHealth.State}" --output table
aws ecs describe-services --cluster shop --services api \
  --query "services[0].{desired:desiredCount,running:runningCount,rollout:deployments[0].rolloutState}"
aws rds describe-db-instances --db-instance-identifier shop-db \
  --query "DBInstances[0].{status:DBInstanceStatus,multiAZ:MultiAZ,az:AvailabilityZone,standby:SecondaryAvailabilityZone}"
```

<Mistakes>

<Mistake title="One of everything">

<Wrong>

```text
One EC2 instance running Nginx + Django + PostgreSQL + Redis in a public subnet: a single failure takes it all down.
```

</Wrong>

<Right>

```text
Separate tiers, managed data services, ≥ 2 AZs for every tier, private subnets for app and data.
```

</Right>

</Mistake>

<Mistake title="Skipping the async tier">

<Wrong>

```text
Sending emails and generating reports inside web requests → slow pages and timeouts at the ALB.
```

</Wrong>

<Right>

```text
SQS + workers (Celery or Lambda) for slow work; the web tier stays fast and scales on its own.
```

</Right>

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="Design a highly available web application on AWS.">

Route 53 and CloudFront (with WAF) in front; an ALB in public subnets across at least two AZs; stateless application containers on ECS Fargate (or an EC2 Auto Scaling group) in private subnets with autoscaling; RDS Multi-AZ (plus read replicas if needed) and ElastiCache with replicas in private data subnets; S3 for files; security groups chained tier to tier, IAM roles, Secrets Manager; CloudWatch alarms; backups, IaC and CI/CD for repeatable deployments.

</QA>

<QA q="Why should the application tier be stateless?">

So any instance or task can serve any request and can be added, replaced or removed by autoscaling and deployments without losing data or logging users out. State goes to shared services: sessions in Redis/DynamoDB, files in S3, data in the database.

</QA>

<QA q="How do the tiers' security groups work together?">

The ALB's group allows HTTPS from the internet (or CloudFront); the app's group allows its port only from the ALB's group; the database and cache groups allow their ports only from the app's group. Each tier accepts traffic only from the tier above it, so the data tier is never reachable from outside.

</QA>

| Tier | Services | Access |
| --- | --- | --- |
| 1 Edge | Route 53 · CloudFront + WAF · ALB + ACM | internet → 443 |
| 2 App | ECS Fargate / EC2 ASG · SQS + workers | from ALB SG only |
| 3 Data | RDS Multi-AZ · ElastiCache · S3 | from app SG only |
| HA | ≥ 2 AZs everywhere | — |
| Scale | autoscaling · caching · read replicas | — |
| Security | private subnets · SG chaining · task roles · Secrets Manager | — |
| Ops | CloudWatch · backups · IaC · CI/CD | — |
