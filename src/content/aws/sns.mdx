<Analogy>

A **WhatsApp broadcast list**. You send one message ("Order 848 placed") to the list (the **topic**), and everyone on the list gets their own copy at the same time: the email team, the warehouse, the analytics team. Someone who only cares about big orders can set a filter so they only see those.

</Analogy>

## Simple explanation

| Concept | Meaning |
| --- | --- |
| **Topic** | the channel you publish to (`order-placed`) |
| **Publisher** | your app: `sns.publish(TopicArn=..., Message=...)` |
| **Subscription** | an endpoint that receives every message: SQS, Lambda, HTTPS, email, SMS, mobile push, Firehose |
| **Filter policy** | per subscription, on message attributes (or body): `{"total": [{"numeric": [">=", 500]}]}` |
| **FIFO topic** | ordered + deduplicated, delivers to FIFO queues |

**SQS vs SNS in one line**: SQS is **one message → one consumer** (pull, work distribution); SNS is **one message → many subscribers** (push, broadcast).

**Fan-out pattern (SNS → several SQS queues)**: each service gets its own queue with its own retries, DLQ and pace. Adding a new consumer = adding a subscription; the publisher does not change.

Details:

- SNS pushes and retries (with a delivery policy for HTTP); it does **not store** messages for later reading, so put an SQS queue in front of consumers that may be down
- **Raw message delivery** sends the plain message instead of the SNS JSON envelope
- The queue's access policy must allow the topic to `sqs:SendMessage`
- Message size up to 256 KB; message attributes used for filtering
- Mobile push via APNs/FCM; SMS has per-country rules and costs; for real email campaigns use **SES**

## Code example

```python
import boto3, json

sns = boto3.client("sns", region_name="ap-south-1")
sqs = boto3.client("sqs", region_name="ap-south-1")
topic = sns.create_topic(Name="order-placed")["TopicArn"]

queues = {}
for name in ["email-q", "inventory-q", "analytics-q"]:
    url = sqs.create_queue(QueueName=name)["QueueUrl"]; queues[name] = url
    arn = sqs.get_queue_attributes(QueueUrl=url, AttributeNames=["QueueArn"])["Attributes"]["QueueArn"]
    attrs = {"RawMessageDelivery": "true"}
    if name == "analytics-q":                                  # only big orders
        attrs["FilterPolicy"] = json.dumps({"total": [{"numeric": [">=", 500]}]})
    sns.subscribe(TopicArn=topic, Protocol="sqs", Endpoint=arn, Attributes=attrs)

for total in [848, 199]:
    sns.publish(TopicArn=topic, Message=json.dumps({"order_id": total, "total": total}),
                MessageAttributes={"total": {"DataType": "Number", "StringValue": str(total)}})

for name, url in queues.items():
    msgs = sqs.receive_message(QueueUrl=url, MaxNumberOfMessages=10).get("Messages", [])
    print(" ", name, [json.loads(m["Body"])["total"] for m in msgs])
```

```output
  email-q [848, 199]
  inventory-q [848, 199]
  analytics-q [848]
```

(Run against a mock of AWS.) One publish reached three queues; the filter kept the ₹199 order out of analytics.

<Mistakes>

<Mistake title="Publishing to several queues yourself">

<Wrong>

```python
sqs.send_message(QueueUrl=email_q, ...)
sqs.send_message(QueueUrl=inventory_q, ...)   # every new consumer = change + deploy the order service
```

</Wrong>

<Right>

```python
sns.publish(TopicArn=order_placed, ...)       # consumers subscribe themselves
```

</Right>

</Mistake>

<Mistake title="Subscribing a fragile HTTP endpoint directly">

<Wrong>

```text
SNS → https://partner.example.com/hook; partner down for an hour → messages dropped after retries.
```

</Wrong>

<Right>

```text
SNS → SQS (with DLQ) → a worker that calls the partner with its own retries; or set a subscription DLQ.
```

</Right>

<QA q="What is the difference between SNS and SQS?">

SNS is pub/sub: a message published to a topic is pushed to all subscribers immediately and is not stored for later polling. SQS is a queue: messages are stored until a consumer polls, processes and deletes them, with each message handled by one consumer. They are often combined: SNS fans out to several SQS queues.

</QA>

<QA q="What is the SNS–SQS fan-out pattern?">

A producer publishes to one SNS topic, and multiple SQS queues subscribe to it. Each downstream service consumes from its own queue independently, with its own scaling, retries and DLQ; new services can be added by subscribing without touching the producer. Filter policies limit what each queue receives.

</QA>

<QA q="How do SNS filter policies work?">

A JSON policy on a subscription matches message attributes (or the message body with payload-based filtering) using exact values, prefixes, numeric ranges, anything-but and exists conditions. Only matching messages are delivered to that subscriber, so the publisher sends once and filtering happens in SNS.

| Item | Remember |
| --- | --- |
| Model | pub/sub · push · one message → many |
| Subscribers | SQS · Lambda · HTTPS · email · SMS · mobile push · Firehose |
| Fan-out | SNS → several SQS queues (each with DLQ) |
| Filter | `FilterPolicy` on attributes / body |
| Plain body | `RawMessageDelivery: true` |
| Order | FIFO topic → FIFO queues |
| Permissions | queue policy allows the topic `sqs:SendMessage` |
| Real email | SES |
