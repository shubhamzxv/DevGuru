<Analogy>

A huge **post-office sorting wall**. Every letter goes into the box for its **partition key** (the pin code), and inside a box letters are kept in order by **sort key** (date). Finding all of Asha's letters from November is instant. Asking "find every letter mentioning headphones" means opening every box (**Scan**): slow and expensive.

</Analogy>

## Simple explanation

| Concept | Meaning |
| --- | --- |
| **Table** | collection of items; no fixed schema except the key |
| **Item** | a record (up to 400 KB), attributes like JSON |
| **Partition key (PK)** | decides which partition stores the item; must spread load |
| **Sort key (SK)** | optional; orders items with the same PK, allows `begins_with`, `between` |
| **GSI** | global secondary index: another PK/SK to query by (eventually consistent) |
| **LSI** | same PK, different sort key (defined at creation) |

**Operations**

| Operation | Cost / speed |
| --- | --- |
| `GetItem` (full key) | fastest |
| `Query` (one PK, SK conditions) | fast, reads only matching items |
| `Scan` (whole table) | slow and expensive; avoid in request paths |
| `PutItem`, `UpdateItem`, `DeleteItem` | with **condition expressions** for safe writes |
| `TransactWriteItems` | all-or-nothing across items (up to 100) |
| `BatchGetItem` / `BatchWriteItem` | many items in one call |

**Design for access patterns first** (the opposite of SQL normalisation). List the questions: "get user profile", "latest orders of a user", "orders by status". Then choose keys, often in a **single table**:

| PK | SK | Attributes |
| --- | --- | --- |
| `USER#42` | `PROFILE` | name |
| `USER#42` | `ORDER#2026-11-14#4` | total, status |
| `USER#42` | `ORDER#2026-11-01#1` | total, status |

**Capacity**: **on-demand** (pay per request, no planning; the usual start) or **provisioned** (RCU/WCU with autoscaling; cheaper for steady load). Reads are eventually consistent by default (strongly consistent costs double, not on GSIs).

Extras: **TTL** to auto-delete expired items (sessions, carts), **Streams** to trigger Lambda on changes, **DAX** in-memory cache, point-in-time recovery, global tables (multi-Region active-active).

DynamoDB vs RDS: DynamoDB for known access patterns, huge scale, serverless, simple key lookups; RDS for joins, ad-hoc queries, complex transactions and reporting.

## Code example

```python
import boto3
from boto3.dynamodb.conditions import Key

t = boto3.resource("dynamodb", region_name="ap-south-1").create_table(
    TableName="orders", BillingMode="PAY_PER_REQUEST",
    KeySchema=[{"AttributeName": "pk", "KeyType": "HASH"}, {"AttributeName": "sk", "KeyType": "RANGE"}],
    AttributeDefinitions=[{"AttributeName": "pk", "AttributeType": "S"}, {"AttributeName": "sk", "AttributeType": "S"}])
for item in [{"pk": "USER#42", "sk": "ORDER#2026-11-01#1", "total": 450, "status": "delivered"},
             {"pk": "USER#42", "sk": "ORDER#2026-11-14#4", "total": 848, "status": "paid"},
             {"pk": "USER#42", "sk": "PROFILE", "name": "Asha"},
             {"pk": "USER#7", "sk": "ORDER#2026-11-10#3", "total": 199, "status": "paid"}]:
    t.put_item(Item=item)

print("get:", t.get_item(Key={"pk": "USER#42", "sk": "PROFILE"})["Item"])
q = t.query(KeyConditionExpression=Key("pk").eq("USER#42") & Key("sk").begins_with("ORDER#"),
            ScanIndexForward=False)                                   # newest first
print("query:", [(i["sk"], int(i["total"])) for i in q["Items"]])

t.update_item(Key={"pk": "USER#42", "sk": "ORDER#2026-11-14#4"}, UpdateExpression="SET #s = :s",
              ExpressionAttributeNames={"#s": "status"}, ExpressionAttributeValues={":s": "shipped"})
print("updated:", t.get_item(Key={"pk": "USER#42", "sk": "ORDER#2026-11-14#4"})["Item"]["status"])

try:
    t.put_item(Item={"pk": "USER#42", "sk": "PROFILE", "name": "X"}, ConditionExpression="attribute_not_exists(pk)")
except t.meta.client.exceptions.ConditionalCheckFailedException as e:
    print("conditional:", e.response["Error"]["Code"])
```

```output
get: {'pk': 'USER#42', 'sk': 'PROFILE', 'name': 'Asha'}
query: [('ORDER#2026-11-14#4', 848), ('ORDER#2026-11-01#1', 450)]
updated: shipped
conditional: ConditionalCheckFailedException
```

(Run against a mock of AWS.) `status` is a reserved word, hence `#s`. The condition stops a second create from overwriting the profile.

<Mistakes>

<Mistake title="Scan with a filter">

<Wrong>

```python
t.scan(FilterExpression=Attr("status").eq("paid"))   # reads (and bills) the whole table, then filters
```

</Wrong>

<Right>

```python
t.query(IndexName="status-index", KeyConditionExpression=Key("status").eq("paid"))
```

</Right>

</Mistake>

<Mistake title="A hot partition key">

<Wrong>

```text
pk = "2026-11-15" for every order of the day: all writes hit one partition → throttling.
```

</Wrong>

<Right>

```text
High-cardinality keys (USER#id, ORDER#id); if needed, shard the key (DATE#2026-11-15#7) and query the shards.
```

</Right>

</Mistake>

<InterviewQA>

<QA q="What are partition keys and sort keys in DynamoDB?">

The partition key is hashed to choose the physical partition and, alone or with the sort key, forms the primary key. The sort key orders items sharing a partition key and enables range queries such as begins_with or between. Good partition keys have many distinct values with evenly spread traffic.

</QA>

<QA q="What is the difference between Query and Scan?">

Query reads items for one partition key value, optionally filtered by sort-key conditions, so it touches only the needed data. Scan reads every item in the table or index and applies filters afterwards, consuming capacity for all items read; it is meant for exports and maintenance, not request paths.

</QA>

<QA q="When would you choose DynamoDB over a relational database?">

When access patterns are known and key-based, you need predictable low latency at large or spiky scale, serverless operation with no connection limits, or global tables. Choose a relational database for complex joins, ad-hoc queries, reporting and evolving query needs.

</QA>

<CheatSheet>

| Need | Use |
| --- | --- |
| One item | `get_item(Key=...)` |
| Items of one PK | `query(KeyConditionExpression=Key("pk").eq(..) & Key("sk").begins_with(..))` |
| Other lookups | GSI |
| Safe create | `ConditionExpression="attribute_not_exists(pk)"` |
| Reserved words | `ExpressionAttributeNames={"#s": "status"}` |
| All-or-nothing | `transact_write_items` |
| Expire | TTL |
| React to changes | Streams → Lambda |
| Capacity | on-demand · provisioned + autoscaling |
| Avoid | Scan in APIs · hot partition keys |

</CheatSheet>
