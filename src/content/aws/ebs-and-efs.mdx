<Analogy>

**EBS** is an external **hard drive plugged into one laptop**: fast, yours alone, and it stays in the same room (AZ). A **snapshot** is a photo backup of that drive you can restore anywhere. **EFS** is a **shared office network drive**: everyone in every room can open the same folders at once, and it grows as you add files.

</Analogy>

## Simple explanation

| | **EBS** | **EFS** | **S3** | Instance store |
| --- | --- | --- | --- | --- |
| Type | block (a disk) | file (NFS) | object (API) | block |
| Attached to | one instance (Multi-Attach for io2 only) | many instances, ECS, Lambda | anything via HTTPS | that host only |
| Scope | one AZ | Region (multi-AZ) | Region | the host |
| Size | you provision (1 GiB–64 TiB) | grows automatically | unlimited | fixed by type |
| Survives stop | yes | yes | yes | **no** |
| Use | root disks, databases on EC2 | shared uploads, CMS, ML data | media, backups, static sites | cache, scratch |

**EBS volume types**

| Type | For |
| --- | --- |
| **gp3** (SSD) | default: 3,000 IOPS + 125 MB/s baseline, tune separately |
| **io2 Block Express** | critical DBs needing high, consistent IOPS |
| st1 / sc1 (HDD) | big sequential data / cold data |

**Snapshots**: incremental backups stored in S3 (you do not see the bucket); copy across Regions; create an AMI from them; automate with **Data Lifecycle Manager** or **AWS Backup**. To move a volume to another AZ: snapshot → create a volume from it in the new AZ. Volumes can be **resized and changed type online** (then grow the filesystem: `growpart` + `resize2fs`/`xfs_growfs`). Encrypt with KMS (turn on encryption by default per Region).

**EFS**: mount with NFS from instances in any AZ via mount targets; storage classes Standard and Infrequent Access with lifecycle; throughput modes (elastic is the default). Great for shared content; slower and pricier per GB than EBS for a single server; Windows shares use **FSx for Windows**, high-performance HPC uses **FSx for Lustre**.

## Code example

```bash
# Create and attach a 50 GB gp3 data volume in the same AZ as the instance
aws ec2 create-volume --availability-zone ap-south-1a --size 50 --volume-type gp3 --encrypted
aws ec2 attach-volume --volume-id vol-0a1b2c3d4e5f67890 --instance-id i-bfb0cc7b362fd8b75 --device /dev/xvdf

# On the instance: format once and mount
lsblk
sudo mkfs -t xfs /dev/nvme1n1
sudo mkdir /data && sudo mount /dev/nvme1n1 /data
df -h /data
```

```output
NAME          SIZE TYPE MOUNTPOINT
nvme0n1        20G disk
└─nvme0n1p1    20G part /
nvme1n1        50G disk
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme1n1     50G  390M   50G   1% /data
```

```bash
# Snapshot before an upgrade
aws ec2 create-snapshot --volume-id vol-0a1b2c3d4e5f67890 --description "before postgres 17 upgrade"

# EFS on two instances (amazon-efs-utils installed)
sudo mount -t efs -o tls fs-0123456789abcdef0:/ /mnt/shared
```

Add the mount to `/etc/fstab` (with `nofail`) so it survives reboots.

<Mistakes>

<Mistake title="Expecting EBS to work across AZs">

<Wrong>

```text
Attach vol in ap-south-1a to an instance in ap-south-1b → error: volume and instance must be in the same AZ.
```

</Wrong>

<Right>

```text
Snapshot → create a volume in the target AZ, or use EFS/S3 for data that many AZs need.
```

</Right>

</Mistake>

<Mistake title="Data on the instance store">

<Wrong>

```text
Database files on an i4i instance-store disk; the instance stops → all data lost.
```

</Wrong>

<Right>

```text
Instance store only for caches/temp; durable data on EBS (with snapshots), RDS or S3.
```

</Right>

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What is the difference between EBS, EFS and S3?">

EBS is block storage attached to one EC2 instance in one AZ, like a disk, ideal for boot volumes and databases. EFS is a managed NFS file system mountable by many instances and containers across AZs, for shared files. S3 is object storage accessed over an API with virtually unlimited capacity, for media, backups and static content.

</QA>

<QA q="How do EBS snapshots work?">

They are point-in-time, incremental backups of a volume stored durably in S3: the first copies all used blocks, later ones only changed blocks. You can restore volumes from them in any AZ of the Region, copy them to other Regions or accounts, create AMIs, and automate them with Data Lifecycle Manager or AWS Backup.

</QA>

<QA q="Which EBS volume type would you choose by default?">

gp3: SSD with a baseline of 3,000 IOPS and 125 MB/s that can be raised independently of size, and cheaper than gp2. Choose io2 Block Express for databases requiring very high, consistent IOPS, and HDD types for large sequential workloads.

</QA>

<CheatSheet>

| Need | Service |
| --- | --- |
| Disk for one instance | EBS gp3 (io2 for heavy DBs) |
| Backup a disk | snapshot · AWS Backup · DLM |
| Move to another AZ | snapshot → new volume |
| Grow a disk | modify-volume → `growpart` + `xfs_growfs` |
| Shared Linux files | EFS (NFS) |
| Windows shares / HPC | FSx for Windows / FSx for Lustre |
| Temporary fast disk | instance store (lost on stop) |
| Objects | S3 |

</CheatSheet>
