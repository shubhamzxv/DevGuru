<Analogy>

Coding is building **one room**; system design is drawing the **plan of the whole building**: where the entrances are, how many lifts you need for rush hour, where the water tank sits, what happens if one staircase is blocked, and how to add floors later without knocking the building down.

</Analogy>

## Simple explanation

**System design** answers: "How do we build this so it works for **many users**, stays **up**, stays **fast**, and is **affordable** to run and change?"

**Two kinds of requirements**

| Kind | Question | Example (food delivery app) |
| --- | --- | --- |
| **Functional** | what must it do? | browse restaurants, place order, track rider |
| **Non-functional** | how well? | 1 M daily users, p99 < 300 ms, 99.9% uptime, no lost orders |

**Building blocks** you combine:

| Block | Job |
| --- | --- |
| Client (web, mobile) | UI |
| DNS, CDN | find the service, serve static files near users |
| Load balancer | spread traffic over servers |
| App servers / services | business logic (stateless) |
| Database (SQL / NoSQL) | source of truth |
| Cache (Redis) | fast reads |
| Message queue | async work, buffering |
| Object storage (S3) | files, images |
| Search index | full-text search |
| Monitoring | logs, metrics, traces |

**The interview process (45 minutes)**

1. **Requirements** (5 min): functional + non-functional; ask about scale
2. **Estimates** (5 min): users, requests per second, storage — "back-of-the-envelope"
3. **API design**: main endpoints
4. **Data model**: main tables/keys
5. **High-level design**: boxes and arrows from client to database
6. **Deep dives**: the hard part (scaling the database, caching, consistency, failures)
7. **Trade-offs & wrap-up**: what you chose and why, bottlenecks, what you would add next

There is **no single correct answer**; interviewers judge how you reason about **trade-offs** (consistency vs availability, cost vs speed, simplicity vs flexibility).

**Handy numbers**: 1 day ≈ 86,400 s ≈ **10⁵ s**; 1 M requests/day ≈ **12 req/s** on average (peak often 2–10×); reading from memory ~100 ns, SSD ~100 µs, a network round trip in one region ~0.5 ms, across continents ~150 ms.

## Code example

A back-of-the-envelope estimate in code:

```python
daily_users = 2_000_000
orders_per_user_per_day = 0.5
reads_per_order = 20                    # browsing menus, tracking
avg_order_size_kb = 2
peak_factor = 5                         # dinner rush

seconds_per_day = 86_400
writes_per_sec = daily_users * orders_per_user_per_day / seconds_per_day
reads_per_sec = writes_per_sec * reads_per_order
storage_per_year_gb = daily_users * orders_per_user_per_day * avg_order_size_kb * 365 / 1024 / 1024

print(f"average writes/s: {writes_per_sec:,.0f}   peak: {writes_per_sec * peak_factor:,.0f}")
print(f"average reads/s:  {reads_per_sec:,.0f}   peak: {reads_per_sec * peak_factor:,.0f}")
print(f"order storage per year: {storage_per_year_gb:,.0f} GB")
print("read/write ratio:", reads_per_order, ": 1  → read-heavy: cache + read replicas help")
```

```output
average writes/s: 12   peak: 58
average reads/s:  231   peak: 1,157
order storage per year: 696 GB
read/write ratio: 20 : 1  → read-heavy: cache + read replicas help
```

<Mistakes>

<Mistake title="Jumping straight to boxes">

<Wrong>

```text
"We'll use Kafka, Cassandra and Kubernetes" in the first minute, before knowing the scale or features.
```

</Wrong>

<Right>

```text
Ask: who are the users, how many, which features matter most, read- or write-heavy, latency and uptime goals.
```

</Right>

</Mistake>

<Mistake title="Designing for imaginary scale">

<Wrong>

```text
50 microservices and global sharding for an app with 2,000 users.
```

</Wrong>

<Right>

```text
Start simple (one service + database + cache), show where it breaks as traffic grows, and how you would evolve it.
```

</Right>

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="How do you approach a system design interview?">

Clarify functional and non-functional requirements, estimate traffic and storage, define the main APIs and data model, draw a high-level design from client to storage, then deep-dive into the hardest parts (scaling, caching, consistency, failure handling), discussing trade-offs and bottlenecks throughout, and finish with improvements.

</QA>

<QA q="What are non-functional requirements?">

Qualities the system must have rather than features: scalability, latency, throughput, availability, durability, consistency, security, cost and maintainability. They drive most design choices, e.g. 99.99% availability forces redundancy across zones.

</QA>

<QA q="Why do back-of-the-envelope estimates?">

To size the system and spot the bottleneck early: requests per second decide how many servers and whether caching is needed, storage growth decides the database and sharding, and the read/write ratio suggests replicas or caches.

</QA>

| Deep dive | bottleneck, failures, consistency |
| Wrap-up | trade-offs, next steps |
