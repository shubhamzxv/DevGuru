<Analogy>

There are two ways to ask a colleague for something.

You can **phone** them: you wait on the line until they answer. If they are busy, you are stuck. That is **synchronous** communication (REST, gRPC).

Or you can **leave a note in their inbox** and carry on with your work. They handle it when they are free, and nothing is lost if they are on a break. That is **asynchronous** communication (a message queue).

</Analogy>

## Simple explanation

**Synchronous**: the caller sends a request and **waits** for the response.

- **REST over HTTP + JSON**: simple, human-readable, works everywhere, easy to debug with curl. The most common choice, especially for public APIs
- **gRPC**: uses HTTP/2 and **Protocol Buffers** (a compact binary format described in a `.proto` file). Faster and smaller than JSON, with strict typed contracts and generated client code, plus streaming. Common for internal service-to-service calls. Harder to debug by hand and not directly usable from browsers

Use synchronous calls when the caller **needs the answer right now**: "is this payment approved?", "what is this user's address?".

**Asynchronous**: the sender puts a **message** on a broker and moves on. A consumer processes it later.

- **Queue** (Amazon SQS, RabbitMQ): each message is processed by **one** consumer. Good for jobs: send this email, resize this image
- **Pub/sub or event stream** (Kafka, SNS, RabbitMQ topics): an **event** such as `order.placed` is delivered to **every** subscriber; billing, shipping and analytics all react

Use asynchronous messages when the work can happen later, when many services must react, or to absorb traffic spikes: the queue holds the messages while consumers catch up.

| Point | REST | gRPC | Message queue |
| --- | --- | --- | --- |
| Style | request and wait | request and wait | send and move on |
| Format | JSON text | Protobuf binary | any (usually JSON) |
| Speed | good | faster | not instant by design |
| Coupling | caller needs callee up | caller needs callee up | services can be down for a while |
| Best for | public APIs, simple calls | internal high-traffic calls | background jobs, events, spikes |

Whatever you choose, plan for failure: **timeouts** on every call, **retries with backoff** for temporary errors, a **circuit breaker** so a dead service is not hammered, and **idempotent** consumers, because queues usually deliver a message **at least once** and it may arrive twice.

## Code example

Synchronous REST call with a timeout and a simple retry:

```python
import time
import httpx

def get_user(user_id: int) -> dict:
    for attempt in range(3):
        try:
            resp = httpx.get(f"http://user-service/users/{user_id}", timeout=2.0)
            resp.raise_for_status()
            return resp.json()
        except (httpx.TimeoutException, httpx.HTTPStatusError) as exc:
            print(f"attempt {attempt + 1} failed: {type(exc).__name__}")
            time.sleep(0.2 * 2 ** attempt)        # wait 0.2s, 0.4s, 0.8s (backoff)
    raise RuntimeError("user-service unavailable")
```

The same contract in gRPC is written once in a `.proto` file; client and server code is generated from it:

```text
syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
message GetUserRequest { int64 id = 1; }
message User { int64 id = 1; string name = 2; string email = 3; }
```

Asynchronous: the Order service publishes, the Email service consumes when it can:

```python
import json

# Order service: publish and return to the user immediately
def on_order_paid(order_id: int, email: str):
    queue.send_message(json.dumps({"type": "order.paid", "order_id": order_id, "email": email}))

# Email service: a separate process that keeps reading the queue
processed = set()

def handle(message: str):
    event = json.loads(message)
    if event["order_id"] in processed:          # idempotent: a duplicate does nothing
        print("duplicate, skipped")
        return
    send_email(event["email"], f"Order {event['order_id']} confirmed")
    processed.add(event["order_id"])
```

```output
email sent for order 1042
duplicate, skipped
```

<Mistakes>

<Mistake title="Calling another service without a timeout">

<Wrong>

```python
resp = requests.get("http://user-service/users/7")   # waits forever if the service hangs
```

</Wrong>

<Right>

```python
resp = requests.get("http://user-service/users/7", timeout=2)
```

</Right>

One slow service then blocks every caller's threads, and the failure spreads through the system (a cascading failure).

</Mistake>

<Mistake title="A consumer that is not idempotent">

<Wrong>

```python
def handle(event):
    wallet.add_money(event["user_id"], event["amount"])   # a redelivered message pays twice
```

</Wrong>

<Right>

```python
def handle(event):
    if payments.already_processed(event["event_id"]):
        return
    wallet.add_money(event["user_id"], event["amount"])
    payments.mark_processed(event["event_id"])
```

</Right>

Most queues deliver at least once. Store the event id and skip duplicates.

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What are the ways microservices communicate?">

Synchronously, with request/response over REST (HTTP + JSON) or gRPC (HTTP/2 + Protocol Buffers), when the caller needs an immediate answer. Asynchronously, through a message broker: point-to-point queues (SQS, RabbitMQ) for jobs handled by one consumer, or publish/subscribe events (Kafka, SNS) delivered to many consumers. Most systems use both.

</QA>

<QA q="REST vs gRPC: when would you pick each?">

REST is simple, human-readable and works from browsers and every tool, so it suits public APIs and simple internal calls. gRPC is faster and smaller thanks to binary Protobuf and HTTP/2, gives strict typed contracts with generated clients, and supports streaming, so it suits high-volume internal service-to-service calls. gRPC is harder to debug and needs a proxy (gRPC-Web) for browsers.

</QA>

<QA q="When should you use a message queue instead of a direct call?">

When the work does not need to finish before replying (emails, reports, image processing), when several services must react to the same event, when you want to absorb traffic spikes, or when the receiving service may be temporarily down. The trade-off is eventual consistency and the need for idempotent consumers and monitoring of queue length.

</QA>

<QA q="How do you make service-to-service calls resilient?">

Set timeouts on every call, retry only temporary failures with exponential backoff and jitter, use a circuit breaker to stop calling a failing service, make operations idempotent so retries are safe, and add fallbacks (cached data or a degraded response). Monitor with distributed tracing.

</QA>

<CheatSheet>

| Need | Use |
| --- | --- |
| Answer right now, public API | REST + JSON |
| Answer right now, internal, high traffic | gRPC |
| One worker does a job later | queue (SQS, RabbitMQ) |
| Many services react to one event | pub/sub (Kafka, SNS) |
| Every network call | timeout + retry with backoff |
| Failing service | circuit breaker |
| Every consumer | idempotent (dedupe by event id) |

</CheatSheet>
