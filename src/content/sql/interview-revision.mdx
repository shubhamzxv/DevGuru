## Simple explanation

Interview SQL comes in two parts:

1. **Theory questions**: short definitions and differences ("WHERE vs HAVING", "what is ACID")
2. **Query writing**: a small problem on a table like `employees` or `orders`

For query problems, use this routine out loud. Interviewers grade the thinking, not only the final query:

1. **Repeat the question** and ask about edge cases: ties, NULLs, empty groups, "what if there is no answer?"
2. **Name the tables and join keys** you need
3. **Decide the shape**: one row per what? That tells you the `GROUP BY` or `PARTITION BY`
4. **Write it in steps** with CTEs, so it is easy to read and fix
5. **Check it** against a small example, including a tie and a NULL

## Theory: the differences they always ask

| Question | Short answer |
| --- | --- |
| `WHERE` vs `HAVING` | `WHERE` filters rows before grouping; `HAVING` filters groups after, and can use aggregates |
| `DELETE` vs `TRUNCATE` vs `DROP` | rows (with WHERE, can roll back) vs all rows fast (DDL) vs the whole table |
| `UNION` vs `UNION ALL` | `UNION` removes duplicates (slower); `UNION ALL` keeps all rows |
| `INNER` vs `LEFT JOIN` | only matches vs all left rows, with NULLs where there is no match |
| `RANK` vs `DENSE_RANK` vs `ROW_NUMBER` | 1,2,2,4 vs 1,2,2,3 vs 1,2,3,4 |
| `IN` vs `EXISTS` | value in a list vs "is there any row"; use `NOT EXISTS`, not `NOT IN`, with NULLs |
| Primary vs unique key | one per table, no NULL vs many, NULL allowed |
| Primary vs foreign key | identifies the row vs points to another table's row |
| Clustered vs non-clustered index | the table is stored in it (one) vs separate structure pointing to rows (many) |
| View vs materialized view | saved query, always fresh vs stored result, needs refresh |
| `COUNT(*)` vs `COUNT(col)` | all rows vs rows where col is not NULL |
| `CHAR` vs `VARCHAR` | fixed length, padded vs variable length |
| Subquery vs CTE vs temp table | inline vs named for one statement vs stored for the session |
| Procedure vs trigger | called with `CALL` vs fires automatically on a data change |
| Normalization vs denormalization | store each fact once vs planned duplication for faster reads |

**ACID**: Atomicity (all or nothing), Consistency (rules hold), Isolation (no half-done work visible), Durability (commits survive crashes).

**Isolation levels**: Read uncommitted → Read committed (PostgreSQL default) → Repeatable read (MySQL default) → Serializable.

**Logical order a query runs in**: `FROM` → `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`. This is why a `SELECT` alias cannot be used in `WHERE`, and why window functions cannot be filtered in `WHERE`.

## Query patterns to know by heart

**1. Second / Nth highest salary**

```sql
SELECT (SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1) AS second_highest;
```

```output
second_highest
--------------
150000
```

**2. Employees earning more than their manager** (self join)

```sql
SELECT e.name FROM employees AS e
JOIN employees AS m ON e.manager_id = m.id
WHERE e.salary > m.salary;
```

```output
name
---------
Imran Ali
```

**3. Highest salary in each department, with the name** (top N per group)

```sql
WITH r AS (
  SELECT department_id, name, salary,
         DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employees WHERE department_id IS NOT NULL
)
SELECT department_id, name, salary FROM r WHERE rnk = 1 ORDER BY department_id;
```

```output
department_id | name           | salary
--------------+----------------+-------
1             | Anita Rao      | 185000
2             | Vikram Shah    | 150000
3             | Meera Nair     | 120000
4             | Farah Sheikh   | 130000
5             | Lakshmi Pillai | 64000
```

**4. Employees above their department's average** (correlated subquery or window)

```sql
WITH a AS (
  SELECT name, department_id, salary, AVG(salary) OVER (PARTITION BY department_id) AS dept_avg
  FROM employees WHERE department_id IS NOT NULL
)
SELECT name, department_id, salary FROM a WHERE salary > dept_avg ORDER BY department_id, salary DESC;
```

```output
name           | department_id | salary
---------------+---------------+-------
Anita Rao      | 1             | 185000
Rohit Verma    | 1             | 140000
Asha Kulkarni  | 1             | 140000
Vikram Shah    | 2             | 150000
Meera Nair     | 3             | 120000
Farah Sheikh   | 4             | 130000
Lakshmi Pillai | 5             | 64000
```

**5. Departments with more than 3 employees** (`HAVING`)

```sql
SELECT d.name, COUNT(*) AS people
FROM employees AS e JOIN departments AS d ON d.id = e.department_id
GROUP BY d.id, d.name
HAVING COUNT(*) > 3;
```

```output
name        | people
------------+-------
Engineering | 7
Sales       | 5
```

**6. Customers who never ordered** (anti join)

```sql
SELECT c.name FROM customers AS c
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id);
```

```output
name
------------
Ritu Agarwal
```

**7. Duplicate values** (`GROUP BY` + `HAVING`)

```sql
SELECT salary, COUNT(*) AS people FROM employees GROUP BY salary HAVING COUNT(*) > 1;
```

```output
salary | people
-------+-------
72000  | 2
140000 | 2
```

**8. Running total by date** (window `SUM`)

```sql
SELECT order_date, COUNT(*) OVER (ORDER BY order_date) AS orders_so_far
FROM orders ORDER BY order_date LIMIT 5;
```

```output
order_date | orders_so_far
-----------+--------------
2024-01-05 | 1
2024-01-12 | 2
2024-02-03 | 3
2024-02-14 | 4
2024-02-28 | 5
```

**9. Month-wise count and change** (group, then `LAG`)

```sql
WITH m AS (SELECT STRFTIME('%Y-%m', order_date) AS month, COUNT(*) AS orders FROM orders GROUP BY month)
SELECT month, orders, orders - LAG(orders) OVER (ORDER BY month) AS change FROM m;
```

```output
month   | orders | change
--------+--------+-------
2024-01 | 2      | NULL
2024-02 | 3      | 1
2024-03 | 2      | -1
2024-04 | 3      | 1
2024-05 | 3      | 0
2024-06 | 3      | 0
```

**10. Pivot: count by status as columns** (conditional aggregation)

```sql
SELECT
  SUM(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) AS delivered,
  SUM(CASE WHEN status = 'shipped'   THEN 1 ELSE 0 END) AS shipped,
  SUM(CASE WHEN status = 'placed'    THEN 1 ELSE 0 END) AS placed,
  SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled
FROM orders;
```

```output
delivered | shipped | placed | cancelled
----------+---------+--------+----------
9         | 2       | 3      | 2
```

<Mistakes>

<Mistake title="Using a SELECT alias in WHERE">

<Wrong>

```sql
SELECT name, salary * 12 AS yearly FROM employees
WHERE yearly > 1500000;          -- MySQL and PostgreSQL: unknown column "yearly" (SQLite allows it)
```

</Wrong>

<Right>

```sql
SELECT name, salary * 12 AS yearly FROM employees
WHERE salary * 12 > 1500000;
```

</Right>

`WHERE` runs before `SELECT`, so the alias does not exist yet in standard SQL. Repeat the expression, or wrap the query in a CTE.

</Mistake>

<Mistake title="Comparing with NULL using =">

<Wrong>

```sql
SELECT COUNT(*) FROM employees WHERE department_id = NULL;   -- 0, always
```

</Wrong>

<Right>

```sql
SELECT COUNT(*) FROM employees WHERE department_id IS NULL;  -- 2
```

</Right>

Any comparison with `NULL` gives unknown, never true. Use `IS NULL` and `IS NOT NULL`.

</Mistake>

</Mistakes>

<InterviewQA>

<QA q="What is the order of execution of a SQL query?">

`FROM` and `JOIN`, then `WHERE`, `GROUP BY`, `HAVING`, `SELECT` (including window functions), `DISTINCT`, `ORDER BY`, and finally `LIMIT` / `OFFSET`. The written order differs from the logical order, which explains why aliases are unavailable in `WHERE` but available in `ORDER BY`.

</QA>

<QA q="How do NULLs behave in SQL?">

`NULL` means unknown. Any comparison with it is unknown, so use `IS NULL`. Aggregates like `SUM`, `AVG` and `COUNT(col)` ignore NULLs; `COUNT(*)` does not. `NULL` values group together in `GROUP BY`. `NOT IN` with a NULL in the list returns no rows. `COALESCE(col, default)` replaces NULLs.

</QA>

<QA q="How do you approach a SQL problem you have not seen before?">

Clarify the expected output and the edge cases; identify the tables and join keys; decide the grain of the result (one row per what); build it step by step with CTEs; then test it mentally on a small example including ties and NULLs, and mention indexes if performance comes up.

</QA>

</InterviewQA>

<CheatSheet>

| Problem | Tool |
| --- | --- |
| Nth highest | `DENSE_RANK` or `DISTINCT ... LIMIT 1 OFFSET N-1` |
| Compare row with its parent | self join |
| Top N per group | `ROW_NUMBER` / `DENSE_RANK` + `PARTITION BY` |
| Compare with group average | `AVG(...) OVER (PARTITION BY ...)` |
| Filter on a count | `GROUP BY` + `HAVING` |
| Rows with no match | `NOT EXISTS` or `LEFT JOIN ... IS NULL` |
| Duplicates | `GROUP BY ... HAVING COUNT(*) > 1` |
| Running total | `SUM(...) OVER (ORDER BY ...)` |
| Change from previous | `LAG(...) OVER (ORDER BY ...)` |
| Rows into columns | `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` |
| Hierarchy, any depth | recursive CTE |
| Slow query | `EXPLAIN ANALYZE`, index, sargable `WHERE` |

</CheatSheet>
