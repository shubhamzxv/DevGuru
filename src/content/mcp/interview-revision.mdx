## Simple explanation

**In one breath**: MCP is an **open JSON-RPC protocol** that lets an AI **host** application connect, through one **client** per connection, to **servers** that expose **tools, resources and prompts**, over **stdio** or **Streamable HTTP**.

**MCP vs function calling vs REST**

| | **Function calling** | **MCP** | **REST API** |
| --- | --- | --- | --- |
| What it is | a feature of an LLM API | a protocol between AI apps and tool servers | a web API style |
| Who talks | your app ↔ model | host/client ↔ server | any program ↔ service |
| Discovery | you hard-code the tool list | `tools/list` at run time | docs / OpenAPI |
| Reuse | per application | any MCP host | any HTTP client |
| Relationship | the host still uses it to show MCP tools to the model | sits **between** the app and your systems | often what an MCP server wraps |

**The request flow** (the "explain end to end" question):

1. Host connects to servers and lists their tools
2. User asks; host sends message + tool definitions to the LLM
3. LLM returns a tool call
4. Host checks permission and sends `tools/call` through the right client
5. Server validates, runs, returns `content` / `structuredContent` / `isError`
6. Host gives the result to the LLM; it answers or calls another tool

**Spec versions to mention**:

| Version | Remember |
| --- | --- |
| `2024-11-05` | first release; stdio and HTTP+SSE |
| `2025-03-26` | Streamable HTTP, OAuth-based authorization |
| `2025-06-18` | elicitation, structured tool output |
| `2025-11-25` | tasks and other additions |
| `2026-07-28` | **stateless**: no `initialize`, per-request `_meta`, `server/discover`, multi round-trip requests; sampling, roots, logging and HTTP+SSE deprecated |

**One line each**

| Topic | Say this |
| --- | --- |
| Host / client / server | app / per-server connector / capability provider |
| Tools | model-controlled actions with JSON Schema inputs |
| Resources | app-controlled read-only data by URI |
| Prompts | user-controlled templates |
| stdio | local subprocess, newline-delimited JSON, logs on stderr |
| Streamable HTTP | remote, POST to one endpoint, OAuth 2.1 |
| Tool error | result with `isError: true` |
| Protocol error | JSON-RPC error code |
| Security | least privilege, approvals, trusted and pinned servers, audience-checked tokens |

## Code example

The whole flow in one real run: a server, a client, discovery, a successful call and a failed one:

```python
import asyncio
from mcp import Client
from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("library", version="1.0.0")
BOOKS = {"B1": "Clean Code", "B2": "Fluent Python"}

@mcp.tool()
def find_book(book_id: str) -> str:
    """Return the title of a book by its id."""
    if book_id not in BOOKS:
        raise ToolError(f"No book {book_id}. Try one of: {', '.join(BOOKS)}")
    return BOOKS[book_id]

@mcp.resource("library://catalogue")
def catalogue() -> str:
    """All book ids and titles."""
    return "; ".join(f"{k}={v}" for k, v in BOOKS.items())

@mcp.prompt()
def recommend(topic: str) -> str:
    """Recommend a book on a topic."""
    return f"Using the catalogue, recommend one book about {topic}."

async def main():
    async with Client(mcp) as client:
        print("1. server   :", client.server_info.name, "| protocol", client.protocol_version)
        print("2. tools    :", [t.name for t in (await client.list_tools()).tools])
        print("   resources:", [str(r.uri) for r in (await client.list_resources()).resources])
        print("   prompts  :", [p.name for p in (await client.list_prompts()).prompts])
        ok = await client.call_tool("find_book", {"book_id": "B2"})
        print("3. call     :", ok.content[0].text, "| is_error", ok.is_error)
        bad = await client.call_tool("find_book", {"book_id": "B9"})
        print("4. failure  :", bad.content[0].text, "| is_error", bad.is_error)

asyncio.run(main())
```

```output
1. server   : library | protocol 2026-07-28
2. tools    : ['find_book']
   resources: ['library://catalogue']
   prompts  : ['recommend']
3. call     : Fluent Python | is_error False
4. failure  : Error executing tool find_book: No book B9. Try one of: B1, B2 | is_error True
```

<InterviewQA>

<QA q="Explain MCP to a backend engineer in two minutes.">

MCP is like a plug standard between AI applications and your systems. You write a small server that exposes a few functions (tools), readable data (resources) and prompt templates over JSON-RPC, either as a local process on stdio or a remote HTTP service with OAuth. Any MCP-capable application can discover those capabilities at run time, show the tools to its model, and route the model's tool calls to your server, with the application controlling permissions.

</QA>

<QA q="MCP vs function calling: what is the difference?">

Function calling is the model-API mechanism by which a model emits a structured request for a function the application defined. MCP is an application-level protocol for discovering and invoking capabilities offered by separate servers. A host uses MCP to obtain tools and function calling to present them to the model; MCP adds standard discovery, transport, auth and reuse across applications.

</QA>

<QA q="When would you build an MCP server and when a plain API integration?">

Build an MCP server when several AI applications or agents should use the capability, when you want users to plug it into existing hosts, or when a team owns the system and should own its AI interface. A direct tool in your own application is enough for a single app with a couple of private functions.

</QA>

<QA q="How would you expose an existing REST service through MCP safely?">

Write a thin server with a few task-level, mostly read-only tools that call the REST API using the server's own credentials; validate inputs with typed schemas; return small structured results and clear errors; separate and gate write actions; deploy over Streamable HTTP with OAuth 2.1, audience and scope checks and per-user authorization; log every call; and test with the in-memory client and the Inspector.

</QA>

<QA q="Why was MCP made stateless?">

Session-based connections needed sticky routing or shared session storage, which complicated load balancing, autoscaling and serverless hosting, and server-initiated requests required long-lived streams. Making each request self-contained lets any instance serve it, lets gateways route on headers, and simplifies caching and retries.

</QA>

<CheatSheet>

| Area | Remember |
| --- | --- |
| Definition | open JSON-RPC protocol: AI apps ↔ tools and data |
| Roles | host (app) → client (1 per server) → server |
| Primitives | tools (model), resources (app), prompts (user) |
| Methods | `server/discover`, `tools/list`, `tools/call`, `resources/read`, `prompts/get` |
| Transports | stdio (local), Streamable HTTP (remote) |
| Stateless | `_meta` on each request; no `initialize`; `resultType` |
| More input | `input_required` → retry with `inputResponses` + `requestState` |
| Errors | tool: `isError: true` · protocol: JSON-RPC code |
| Python | `MCPServer`, `@mcp.tool()`, `mcp.run()`, `Client(...)` |
| Host config | `mcpServers`: `command` + `args` + `env`, or `url` |
| Auth | OAuth 2.1 + PKCE; check audience and scopes |
| Security | least privilege, approvals, pin tools, untrusted results |
| vs function calling | different layer; used together |
| vs REST | MCP wraps APIs for models |

</CheatSheet>
